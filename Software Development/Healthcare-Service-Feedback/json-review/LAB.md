## E. Repeated-use value and baseline
A service analyst could review themes daily or weekly. Repeated counts could make feedback clearer; this is a hypothesis requiring a user trial. Baseline: manual reading of the same synthetic fixture. Success target: exact agreement with the stated expected output and correct rejection/hold behaviour. No timing baseline was measured, so no speed or savings claim is made. AI is omitted because explicit counting and completeness rules meet this slice’s need more simply.
## F. Architecture and boundaries
Local operator → synthetic JSON file → Python validation/rules → JSON output → human reviewer. The operator needs read access to templates and write access to output. The program uses no accounts, network, cloud, API, secret or clinical judgement. A JSON file is a plain text set of named values. References in the launch report are labels, not verified source documents. Production would require approved access, authentic evidence, privacy review and operational/clinical ownership.

## I. Break/fix exercise
Command: python3 scripts/analyse.py --input templates/duplicate.json --output output/rejected.json
Expected: Input rejected: Missing or duplicate ticket id, exit code 2. Verify output/rejected.json does not appear in a fresh folder. This prevents double counting; no existing output is deleted. Recover by returning to templates/sample.json, not by removing validation.
Second fault: change age_hours to -1 in your practice file; expect exit 2 and no fresh output. Restore a non-negative number and repeat. Read the actual error. Do not replace an unrecognised status with an optimistic assumption. Existing reports can be stale after a failed run; check the input path and timestamp before using any report.

# Lab 1 — Integration log diagnosis
## Purpose, company basis and gaps
Build a small offline workbench that separates an authentication refusal, throttling, server failure and missing ingestion. Profound's advert names log reading, queries, reproducible bugs and cloud/CMS integrations. Its Agent Analytics product and developer guides describe website-log integrations. This synthetic scenario is a reasoned learning example, not a claim about an actual Profound incident. It strengthens R04–R07/R11; mail/DNS diagnosis is transferable, but the advertised providers remain new.
Repeated use: a support engineer can inspect each new integration fault and prepare a clear escalation. Baseline is reading a raw JSON file by hand. Target: correct diagnosis of supplied fault classes, isolation between dummy tenants and repeatable evidence. No time-saving baseline was measured; a local test does not prove customer impact. AI is unnecessary for counting known status codes and could obscure deterministic evidence.

## Architecture and prerequisites
Engineer → local JSON fixtures → Python validation → in-memory SQLite → tenant-filtered summary → reviewed escalation note. SQLite is a tiny database inside the process. Parameter binding keeps user text out of SQL code. Dummy tenant filtering is an exercise, not production authentication. No network, cloud credentials, Slack or customer data. Requirements: Python 3.11+ with sqlite3 and a terminal/editor; standard library only, no pip packages. Check the Python version before running. Estimated beginner time: 2–4 hours plus optional provider work. Local cost £0; cloud extension may cost money and needs separate approval/access.
The public source uses src/main.py, tests/, data/, evidence/ and docs/. Start in the project root. For a new clone: git clone https://github.com/Iam4syT/thinkbox.git; then open Software Development/integration-log-workbench. If publication is still pending, use the supplied public folder locally.

## Step 1 — Check a clean environment
Starting state: project files copied locally, no service account needed. Run `python3 --version`; expect 3.11 or newer. Run `python3 -c "import sqlite3; print(sqlite3.sqlite_version)"`; expect a SQLite version. If python3 is absent, use a known Python installation; do not install unknown software. If sqlite3 is unavailable, use a standard Python distribution. Create an isolated environment with `python3 -m venv .venv`, then `source .venv/bin/activate` on macOS/Linux or `.venv\Scripts\Activate.ps1` on Windows. Verify `python --version` matches. No dependency install is required.

## Step 2 — Inspect the dummy input
Open data/logs.json in the editor. Each record has tenant, request_id, numeric HTTP status and accepted (0 or 1). HTTP is the web request/response protocol; 401 means authentication refused, 429 means rate-limited and 503 means service unavailable. In this exercise accepted is a simulated downstream signal. Expect five demo-a rows and one demo-b row. Never paste real tokens, request bodies or customer domains. If a field is missing, restore the supplied fixture rather than guessing a customer value.

## Step 3 — Run the happy path
Run `python src/main.py --tenant demo-a`. Expect counts 200:2, 401:1, 429:1 and 503:1, plus unaccepted_success:1. Read findings: one successful web response lacks downstream acceptance. A 200 alone does not prove the full integration worked. Compare every number to the input by hand. If counts differ, check the current directory, input path and tenant spelling; do not change expected results just to pass.

## Step 4 — Follow the query
Open src/main.py. Find CREATE TABLE, INSERT with placeholders and SELECT ... WHERE tenant=?. Run `python -m unittest discover -s tests -v`; expect nine passing checks. The SQL groups response counts for the selected tenant. Inspect test_parameter_binding: text containing SQL syntax is a value, not executable query. If a test fails, capture the failure and compare the code and fixture before rerunning. An in-memory database disappears when the process closes.

## Step 5 — Verify isolation and empty data
Run `python src/main.py --tenant demo-b`; expect only its one 200 and no demo-a fault rows. Run `python src/main.py --tenant unknown`; expect empty counts and a No data finding. Empty evidence is not proof of a healthy system. Save the output with `python src/main.py --tenant demo-a > evidence/personal-run.json` only after confirming the directory exists. Verify it contains dummy values only. If sensitive input was used accidentally, stop and keep it out of publication.

## Step 6 — Reproduce a fault and recover
Copy data/logs.json to data/broken.json. Change the first status from the number 200 to the quoted text "200". Run `python src/main.py --input data/broken.json --tenant demo-a`; expect ValueError. This proves malformed data is rejected, not diagnosed as success. Restore numeric 200 and rerun; expect the original counts. Then add a duplicate record with the same tenant/request_id; expect unchanged counts because retry duplicates are ignored. This is a toy identity rule; real systems may require event IDs/timestamps. Restore the fixture after each exercise.

## Step 7 — Build an Engineering escalation
Create docs/escalation.md. Write: dummy customer impact; observed time with timezone (your actual run time); request IDs; expected versus actual; command/input used; checks done; suspected area; unknowns; named human owner and next check. Separate evidence from hypothesis. Example: HTTP 200 observed but accepted=0 in the fixture; downstream state needs checking. Do not claim root cause was confirmed. Ask a peer to reproduce using the same fixture. Expected: same result without private information. If not, fix the reproduction instructions and preserve both observations.

## Step 8 — Understand the provider extension, unrun
Read https://docs.tryprofound.com/introduction to choose one provider-specific guide. Cloudflare Worker, Logpush and Vercel routes are different; do not treat them as interchangeable. Record the selected guide URL/check date, required account plan, token permissions, billing and log schema in docs/provider-plan.md. Without authorised test accounts stop at that plan. With separately authorised accounts, follow the current official route, send only dummy traffic and compare source requests, forwarder status and destination receipt. Do not disable security controls or change a live tenant. No provider execution is claimed in this bundle.

## Step 9 — Acceptance and evaluation
Accept the offline slice only if all nine tests pass, demo-a/demo-b remain separate, malformed input fails, retries do not inflate counts and 200-without-acceptance is visible. Save actual command/runtime, result and any failure in EVALUATION.md. Count correctness is checked on six authored records, not real traffic or unseen customer faults. A user-agent string does not authenticate a crawler; this workbench makes no crawler identity claim. Bunamin should explain the SQL, each finding and a limitation in his own words before treating this as personal evidence.

## Step 10 — Cleanup and portfolio story
Close the terminal environment with `deactivate`. Remove only your generated data/broken.json and evidence/personal-run.json if no longer needed; preserve supplied evidence. No cloud resource was created. For any future cloud trial list resources first, disable the test forwarder and remove only the resources you created after reviewing retention/cost requirements. Do not delete customer logs. Portfolio artefacts: source, fixtures, tests, escalation note, actual personal output and a two-minute recording with dummy values. Interview story: recurring fault → offline constraint → query/filter design → malformed/retry failure → checks → useful escalation → provider gap. Conditional CV wording, use only after personal completion and evidence: “Built and tested a local log-query workbench that distinguishes simulated integration faults and produces reproducible escalation evidence.” Optional extension: reviewed live test integration and DNS/HTTP traces, with actual permissions, schema and receipt checks.

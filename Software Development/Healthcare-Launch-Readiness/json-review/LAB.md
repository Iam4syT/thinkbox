## E. Repeated-use value and baseline
A launch coordinator could repeat this check at each change. The intended benefit is fewer overlooked evidence items; no reduction has been measured. Baseline: manual reading of the same synthetic fixture. Success target: exact agreement with the stated expected output and correct rejection/hold behaviour. No timing baseline was measured, so no speed or savings claim is made. AI is omitted because explicit counting and completeness rules meet this slice’s need more simply.
## F. Architecture and boundaries
Local operator → synthetic JSON file → Python validation/rules → JSON output → human reviewer. The operator needs read access to templates and write access to output. The program uses no accounts, network, cloud, API, secret or clinical judgement. A JSON file is a plain text set of named values. References in the launch report are labels, not verified source documents. Production would require approved access, authentic evidence, privacy review and operational/clinical ownership.

## H. Granular lab — start, run and inspect
### 1. Open a writable local copy
Starting state: this project folder has been downloaded or copied. Open a terminal. Type cd followed by a space, then drag the public folder into the terminal and press Enter. This supplies its exact path without guessing. Command: python3 --version

### 2. Inspect data and scope
Starting state: no program has been run. Open templates/sample.json and scripts/check_launch.py in the editor. Read the input and the validation function. All fixtures use invented identifiers and values. Verify there are no real names, patient data or credentials. If your copy contains real information, stop and replace it with the supplied synthetic sample.
### 3. Record the manual baseline
Starting state: the original sample is unchanged. Read templates/sample.json. For training, support_owner, rollback and test_evidence, check that status is passed and evidence is non-blank. Write your answer before running the program. Expect ready-for-human-review. References are just labels; the program cannot authenticate the documents. Save your answer in a local notes file. If you disagree with the stated output, follow each rule in scripts/check_launch.py before editing code. The supplied rules are illustrative, not clinical priorities or contractual service levels.
### 4. Verify the source behaviours
Starting state: the source and tests are unchanged. Command: python3 -m unittest discover -s scripts -p "test_*.py" -v
Expected: eight named tests and OK. Read every test name; check the normal path, incomplete/invalid input and boundary cases. Save the terminal output outside tracked source if practising. If a test fails, inspect its assertion and the affected rule. Restore the supplied code or fix the rule, then rerun; do not delete the failing check to get OK.
### 5. Run the normal example
Starting state: checks pass and templates/sample.json is unchanged. Command: python3 scripts/check_launch.py --input templates/sample.json --output output/result.json
Expected: a printed report and output/result.json created. A complete synthetic checklist returned ready-for-human-review; removing rollback evidence returned hold and named rollback. Neither output grants go-live permission. Open the saved JSON and compare it with your manual answer and evidence/sample-output.json. If the command cannot find a file, confirm the terminal is in the project folder; if it cannot write, move the copy to a writable personal folder.

## H. Granular lab — build a change and hand it over
### 6. Change one input and predict the effect
Starting state: the normal example matches your notes. Copy templates/sample.json to templates/practice.json with your editor. Change training.status from passed to pending. Run with --input templates/practice.json --output output/practice.json. Expect hold with training in missing_or_failed. Restore passed and rerun; expect ready-for-human-review. If JSON is rejected, restore commas and quotes from the original. Keep the original sample so a later run can distinguish a deliberate change from a broken fixture.
### 7. Explain the decision to another person
Starting state: both normal and changed reports exist. In docs/your-handover.md, write the input used, rule that changed the result, output path and the next human action. Verify your note distinguishes a suggestion from an approved action. If you cannot explain a result, trace its input and rule before calling the exercise complete.

If the repeat differs, inspect input edits first, restore the supplied sample and retry.

## I. Break/fix exercise
Command: python3 scripts/check_launch.py --input templates/hold.json --output output/hold.json
Expected: decision hold, missing_or_failed contains rollback. Verify this in output/hold.json. A blank reference is incomplete evidence even when status says passed. Recover by using the unchanged complete sample; do not treat filling a label as proof of real approval.
Second fault: change training.status to done in your practice file; expect exit 2 rather than ready. Restore passed and repeat. Read the actual error. Do not replace an unrecognised status with an optimistic assumption. Existing reports can be stale after a failed run; check the input path and timestamp before using any report.

# Lab 2 — Ticket triage, handoff and knowledge drafts
## Purpose, company basis and gaps
Build a small support queue exercise with a rules baseline, traceable guidance and a simulated AI suggestion guard. Profound's advert asks for AI-assisted triage, regional handoffs, recurring-defect feedback and runbooks. This lab is a reasoned example of those duties, not Profound's internal tooling. It strengthens R03/R08–R10/R13–R16. Professional case work is the foundation; production AI triage, public status updates and Slack automation remain unproven.
Repeated use: a support engineer routes each ticket, checks urgent cases and prepares the next shift's note. Baseline is simple keyword rules with human review. AI might help with varied wording or summaries; it must outperform that baseline on unseen cases without missing urgent faults or inventing fixes. No live model is called here. The suggestion file is a simulation for checking boundaries, not evidence of model accuracy, lower cost or faster support.

## Architecture and prerequisites
Dummy ticket JSON → deterministic priority rules → known knowledge article ID → simulated suggestion checks → human-reviewed handoff draft. Text from a ticket is untrusted data, not instructions to reveal secrets or make changes. Every output remains draft-only; no email, Slack, status page or account change occurs. Python 3.11+, editor and terminal; standard library only. Cost £0 locally, estimated beginner time 2–4 hours. Real model/Slack integration is optional and unrun, with access/cost/permissions reviewed separately. Layout follows src/, tests/, data/, evidence/ and docs/.
For a new clone use git clone https://github.com/Iam4syT/thinkbox.git then open AI Projects/support-triage-workbench. If not yet published, use the local public folder. No service login or API key is required.

## Step 1 — Start and inspect
From the project root run `python3 --version`; expect 3.11+. Create `.venv` with `python3 -m venv .venv` and activate it as in lab 1. Verify `python --version`. Open data/tickets.json and docs/knowledge.md. Expect five synthetic tickets: authentication, throttling, outage mixed with authentication, unknown wording and hostile instructions. Knowledge IDs are KB-auth, KB-rate and KB-incident. These are local teaching notes, not official Profound advice. If files are missing, restore the project package; do not substitute customer data.

## Step 2 — Run the rules baseline
Run `python src/main.py`. Expect routes auth, rate, incident, unknown and unknown in that order. Each output has human_review true, external_actions false and an unassigned human handoff owner. A ticket mentioning all users/outage must outrank a matching 401 word. Compare input and route manually. If output differs, check text and rule order. This baseline is deliberately limited: different wording may be missed, and unknown needs a person.

## Step 3 — Test the ordinary and unsafe paths
Run `python -m unittest discover -s tests -v`; expect ten passing checks. Read test_incident_priority, test_unsafe_action and test_hostile_ticket. They check urgent precedence, rejection of action-taking suggestions and refusal to treat hostile ticket text as a command. If a failure appears, save it before editing and rerun the smallest affected test after correction. Tests do not establish prompt-injection resistance of a real LLM or real tenant isolation.

## Step 4 — Inspect simulated AI suggestions
Open data/suggestions.json. Ticket t1 has route auth, citation KB-auth and action draft_only. Ticket t2 has an invented citation. Run `python src/main.py --suggestions data/suggestions.json`. Expect t1 “simulated suggestion accepted for review” and t2 “simulated suggestion rejected; rules fallback”. Accepted still means a human must check it. Other tickets use rules. Verify no model/API/network call in src/main.py. If malformed JSON causes an error, restore its commas/quotes; do not treat a parse failure as a successful AI run.

## Step 5 — Break, reject and recover
Copy suggestions.json to data/broken.json. Change t1 action to reset_password. Run `python src/main.py --suggestions data/broken.json`; expect t1 rejected with rules fallback. Restore action draft_only, then change citation to invented; expect rejection again. Restore KB-auth; expect accepted for review. Finally change route to incident while keeping the auth ticket: expect rejection. Save the actual outputs. This guard checks a small allowed structure; it is not a full factual verifier. No password is reset.

## Step 6 — Write the customer update and regional handoff
Create docs/handoff.md for the outage ticket. Include actual observation time/timezone, synthetic scope, what the user cannot do, observed facts, checks already performed, unknown cause, owner, next action and next update time. Keep the customer note simple: “We are checking the affected requests. The cause is not confirmed. Our next update is [actual agreed time].” Replace brackets only after deciding a real test schedule. Engineer note: input ID, reproduction command, expected/actual route and evidence path. Have another person read it and state who owns the next step. If nobody is named, it is not an operational handoff yet. Do not publish a status message or pretend the issue is resolved.

## Step 7 — Turn repeated tickets into a knowledge draft
Create docs/kb-draft.md from the authentication example. Include symptom, safe checks, evidence to collect, when to escalate and article source/version. Explain 401 as a refused authentication request. Never ask a customer to paste a token into a ticket or disable access controls. Mark the article awaiting product/security review. Expected: a reader can identify the next safe diagnostic step and its limit. Compare it with docs/knowledge.md, remove any invented product route and record the edit. Actual ticket deflection requires later usage data; no reduction claimed.

## Step 8 — Design a fair AI comparison, unrun
Create data/holdout-plan.md with at least 20 new synthetic cases written before tuning: varied authentication/rate language, high-impact outages, ambiguous reports, irrelevant/hostile instructions and missing context. Record expected route and required abstention with human review. Keep this set separate from training examples. Measure urgent misses, correct route/citation rate, unsupported-action count, review time, latency and model cost. For a real model use only permitted dummy data, an approved provider and capped spend; supply knowledge as reference, never authority for actions. Collect raw inputs/outputs and run configuration. Promote AI only if it adds useful performance against rules while preserving zero unsafe actions and no extra urgent misses on this set; a sample of 20 is still small. Until executed, results and provider cost remain unknown. Model failure must return to rules/human review.

## Step 9 — Acceptance and evidence
Accept the offline slice when ten tests pass, the five supplied tickets route as expected, incident wins over auth, unknown cases abstain, invented citations/unsafe actions are rejected and every handoff stays human-reviewed. Save `python src/main.py --suggestions data/suggestions.json > evidence/personal-run.json`, inspect it and record runtime/command in EVALUATION.md. Supplied assistant tests use five authored tickets and small unit cases; this is not a held-out AI evaluation or an SLA/CSAT test. A static route is not proof of correct resolution. Bunamin must explain the priority rule, a rejected suggestion and a limitation before claiming personal completion.

## Step 10 — Cleanup, story and extension
Deactivate the environment. Remove only your temporary broken.json and personal output if not needed; keep original fixtures/evidence. No remote resource exists. Keep private ticket text, customer identity and account data out of commits. Public artefacts: source/tests, dummy fixtures, knowledge draft, handoff, result and a two-minute demonstration. Interview story: repeated routing need → human-review constraint → rules baseline → unsafe suggestion → rejection/fallback → verification → clearer handoff → real-model comparison next. Conditional CV wording, only after personal completion and evidence: “Built a local support-triage prototype with a rules baseline, cited guidance and reviewed suggestion fallback, then tested urgent and unsafe cases.” Do not call it production AI. Optional extension: read-only ticket export and reviewed draft publishing in a separately authorised test workspace; no autonomous live responses or permission changes.

# Application release and recovery lab
## A Purpose and sourced need
Practise a small database-backed change that can be stopped and recovered safely. Application engineers must keep services updated and documented. The employer's modernisation direction supports this learning need; no internal outage or recovery weakness is alleged. Source https://www.ombudsman.org.uk/our-strategy .
## B Requirement and evidence gap
Targets database queries, testing, release discipline, application support and operational handover. FirstBank SQL queries and support work are the starting evidence. SQLite practice does not establish SQL Server, TSQL, Dynamics 365 development or production recovery ownership.
## C Repeated use and baseline
A support engineer needs a repeatable pre-change check and a verified recovery route for every release. Baseline is a written change checklist and manual schema/data checks. The local code adds a repeatable transaction and regression suite. An AI agent is unnecessary for deterministic schema integrity and could add unsafe variability. No release-time saving is measured.
## D Architecture and scope
Python standard library -> isolated in-memory SQLite -> tickets table -> transaction-scoped schema/data migration -> injected failure -> rollback and backup/restore tests. No network, API, password, persistent production database or Microsoft tenant. Native extension is a supervised Power Platform solution release and a separate SQL Server exercise, not an assumption that Dataverse can be restored by SQL scripts.
## E Prerequisites licences and cost
Python 3.10 or newer; no dependencies or paid resources for local tests. A native exercise needs approved development and test environments, licensing, a solution owner, data owner and backup/restore authority. SQL Server tooling/edition and platform compatibility must be confirmed separately. Never use a real casework database. Microsoft solutions guidance https://learn.microsoft.com/en-us/power-platform/alm/solution-concepts-alm was read 2 November 2026; deployment policies may vary by tenant.
## F Local steps with expected results
1. Open this public project root and run `python3 --version`; confirm 3.10 or newer. Check scripts/release.py and tests/test_release.py exist. If not, correct the working directory before running anything.
2. Read open_db in scripts/release.py. It creates one SYN-1 record in memory and commits the starting state. Run `python3 -B scripts/release.py`. Expected injected-failure rollback True, then successful release with SYN-1, New and operator-a. If output differs, preserve it and inspect the exception/transaction sequence.
3. Run `python3 -B -m unittest discover -s tests -v`. Expected eight tests. They check schema update, preserved values, rollback of schema and data, retry, repeat-release failure, parameterised lookup and backup/restore. A failing assertion is evidence to investigate, not to delete.
4. Examine get_ticket. User-supplied text is passed as a query parameter rather than joined into SQL. The injection-like input must return no row. This is a narrow query-safety test, not a full security audit or a safe arbitrary SQL console.
5. Examine test_backup_restore. A clean in-memory backup is taken, the migration runs and the backup is restored over the test database. Check both schema columns and record values. A row-count-only comparison would miss an incorrect schema; keep both checks. This does not prove any SQL Server restore procedure.
6. Make your own small change in an isolated copy, such as a new required data field. Design a failure after the schema change and before commit. Run the suite and capture your changed source, expected outcome and actual output. Explain why transaction rollback preserves the old schema. Keep assistant test results separate from your own work.
## G Native Power Platform release extension that remains unrun
1. With authorised sandbox access, record separate development and test environment names, solution owner and a change window. Identify dependencies, connection references, environment variables, data policy and rollback owner. Stop if only production access exists.
2. Start from a small solution such as the workflow lab. Keep the unmanaged source in development. Export the agreed version to source control and export a managed package for a separate test environment, following the team's deployment policy. Record package hash and version. Do not invent a successful export.
3. In test, establish a before-state: synthetic rows, permitted/denied user checks, flow enabled state and an ordinary app task. Record expected results and the exact version. Create an approved environment backup or recovery route where supported, but do not assume uninstalling a managed solution preserves data.
4. Import with correct connection references and environment values. Review dependency and import warnings before enabling flows. Recheck the ordinary task, least-privilege denial, one flow run, required fields and duplicate protection. An import success message alone is not acceptance.
5. Exercise one missing connection or environment value. Record the error, restore the correct reference and re-run the failed task. Use a test identity and synthetic data. Do not enter or export connection secrets.
6. Practise recovery using the platform owner's approved method. A previous package import is not a universal rollback: managed upgrades, schema changes and data need separate planning. Verify the restored version and the synthetic record set after recovery. Leave status unrun if no approved recovery access exists.
## H Separate SQL Server practice that remains unrun
Set up only an approved disposable SQL Server instance supported on the actual machine or sandbox. Create a synthetic training database with restricted users. Recreate the tickets schema using TSQL in a reviewed script, use parameterised queries, back up to an approved lab location and test restore to a separate lab database. Verify schema and data as well as access rights. Record edition, version, backup path, permissions and actual restore evidence. SQLite syntax and transaction behaviours must not be treated as identical to SQL Server. No executable TSQL restore script is supplied without a known safe instance and paths.
## I Failure and recovery exercises
Inject RuntimeError after ALTER TABLE locally: old columns and data must remain. Run the release twice: second attempt must fail while preserving the successful first result. Query with injection-like text: no unintended row. Restore the snapshot: original columns and SYN-1 values must return. Native exercises use approved test connections only and remain separate.
## J Acceptance and cleanup
Local acceptance: eight tests pass, expected demo observed, schema/data recovery shown and source reviewed. Native acceptance: two-environment release, actual smoke checks, authorised denial and verified recovery, all recorded. No native pass inferred. Closing the Python connections removes the in-memory database. Remove only lab export/backup copies when no longer needed; preserve permitted evidence. In native environments disable test flows and remove only named lab components after dependency review and owner approval.
## K Evidence and evaluation
Retain test output, source hash, before/after schema and values, exact failure injection and recovery output, plus native checklist with unrun states. Intended success is repeatable detection and recovery, not a fabricated availability percentage. No timing/cost benefit or commercial use is measured.
## L Interview story
Explain why you checked schema and data after rollback, how query parameters limit this injection path and why deployment success is different from a working service. Say clearly that a local SQLite transaction does not prove Power Platform or SQL Server recovery.

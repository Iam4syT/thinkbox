# Lab 2 — Meeting readiness and searchable support guide
## A–E. Outcome, context, mapping and repeat use
Outcome: check a test meeting setup end to end, capture useful fault/handover notes and provide an offline search of approved support cards. This is distinct from joiner provisioning: it exercises live collaboration readiness, diagnosis and knowledge retrieval.
Scenario basis: a hypothetical multidisciplinary studio needs repeatable IT support. No employer deployment or demand has been established.
Scope: independent learning for support operations; physical and tenant work require equipment, authority and actual evidence.
## F. Architecture and simpler baseline
Two authorised test participants/devices → Teams meeting and actual audio/video/share test → ticket/handover → reviewed support card. Offline Python search reads only local synthetic cards, matches words and cites the matching source card. It does not call an LLM, cloud API or Graph, and does not change devices. An indexed folder/SharePoint search is a simpler workplace baseline; use that unless an evaluated assistant improves a real repeated task.
AI extension is optional and unrun: retrieve permitted cards, answer only from them, cite sources, decline unknown or restricted cases, retain a human reviewer. Never send client drawings, recordings, credentials or personal tickets to an AI service. No claim of a workplace-approved AI system.
## G. Prerequisites and costs
Offline: Python 3 and supplied synthetic cards, source/tests; no licence cost/network calls. Real meeting branch: two authorised test users/devices with supported Teams access, permitted headset/camera/display and a remote test participant. A second laptop is a baseline meeting test, not certified Teams Rooms validation. Dedicated Rooms branch requires the actual licensed device/account and owner; absent here. Check current vendor/licence requirements before use . No purchase or live room change is authorised. Offline session and one to three weekends total are planning estimates, not measured time.


## H1. Build a trustworthy offline knowledge baseline
1. Starting state: solution folder on any OS. Run `python3 --version` then `python3 -m unittest discover -s tests -v`. Expected: Python 3 and recorded normal/unknown/restricted input results. Verify actual output. If a test fails, retain it and correct the named failure before the demo.
2. Open `templates/cards.json`. Inspect the three synthetic cards: audio selection, camera check and screen-share permission. Each has id, title and concise steps. Expected: no employee/client detail, promises, passwords or invented employer configuration. Verify manually; replace any private text with dummy text before proceeding.
3. Run `python3 scripts/search.py templates/cards.json audio`. Expected: cited audio card, not a generated diagnosis. Verify displayed id/title matches its source. If not, stop and compare input/schema with the unchanged supplied cards.
4. Run the same search with `quantum`. Expected: NO MATCH — ask IT. Verify the tool does not invent an answer. Recovery: use human diagnosis or author/review a new card when appropriate; never silently add an answer merely to pass the test.
5. Run with `password` and then `admin`. Expected: ESCALATE — use approved IT route. Verify no reset instruction or secret is supplied. Recovery: keep identity-sensitive requests in the authorised process. This toy word rule is not an access-control boundary or comprehensive security filter.
6. Copy `templates/meeting-check.md` to `evidence/my-meeting.md`. Record synthetic meeting purpose, owner, participant, device/app versions, permission and planned checks. Expected: all results start “not run”. Verify operator and test time are actual when filled. Recovery: do not backfill a successful test from memory without labelling it reconstructed.
## H2. Prepare the meeting baseline — unrun
7. Starting state: two permitted test participants/devices and approved application. Agree a short harmless test call, no client drawings, no recording, clear rollback and any room booking. Expected: explicit scope. Verify no real meeting will be disrupted. If permission/equipment is absent, stop at offline branch.
8. On each device open the approved Teams client/browser and verify account and device readiness. Record camera/microphone/display and network connection without exporting identifiers. Expected: correct test accounts. Verify normal sign-in and no unapproved admin access. If sign-in fails, capture error and use approved identity support; do not bypass authentication.


## H3. Test audio, camera and sharing — unrun
9. Starting state: Teams client signed in. Open Settings → Devices (or current Audio/Video device settings) and select the approved speaker and microphone. Where available use Make a test call . Expected: test playback/recording. Verify selected physical device, not only its label. If test call is absent in this client, record that and test with the second participant; do not treat absence as equipment failure.
10. Join the harmless test meeting from both devices. Keep only one loudspeaker active in the same room or use headsets to avoid feedback. Say a short test phrase in both directions. Expected: each participant hears the other clearly. Verify with their explicit reply and record the actual result. Recovery: check mute state, selected input/output, volume, connections and authorised OS permissions; change one variable at a time.
11. Enable the approved camera and ask the remote participant to confirm the image. Expected: correct camera and usable picture. Verify privacy cover/source and remote receipt. Recovery: check camera permission/source, close competing camera apps if permitted, and retry; do not change security policy or install unknown drivers.
12. Create a harmless one-page local document labelled LAB. Share only its application window, not the whole desktop. Expected: remote participant reads the dummy content. Verify by asking them to name a line; record result. Recovery: check Teams/OS screen-sharing permission under owner guidance, stop/restart only the test share, and retry. Do not display email, private files or real drawings.
13. Ask the second participant to share their dummy window and repeat the audio/video checks. Expected: two-way working collaboration. Verify remote receive path separately from local preview. Recovery: note whether issue affects one participant/device/network; collect approved diagnostics and route to owner rather than blame “the network” without evidence.
14. If an approved spare peripheral/display is available, ask a supervisor to demonstrate correct connections and source selection; repeat safely and retest the meeting. Expected: real peripheral task performed and observed. Verify actual output, cables and device selection with supervisor. If none is available, mark physical-room work unrun. Ordinary laptop success does not establish room-system setup or telephone support.


## H4. Break, fix, record and publish a local guide
15. Starting state: working test audio, explicit fault permission. Mute the test microphone in the application. Expected: remote participant cannot hear it. Verify a known reversible fault before diagnosis. Recovery: unmute and repeat the two-way phrase. Record symptom, check, change and actual retest; no fault on shared or live equipment.
16. Starting state: working test camera/share. Close the privacy cover or turn camera off in the test call, observe the failure, restore it and ask remote participant to confirm. Expected: fault and recovery distinguished. Verify the receive path. If recovery fails, retain unresolved outcome and escalate with version/source/checks; do not write “resolved”.
17. Write the support record: impact/urgency, affected scope, evidence, tests, permitted changes, current state, user update, owner and next action. Expected: another engineer understands what happened. Verify there are no secrets or recording links. Recovery: fill missing observations; use “unknown” where not tested and keep escalation open.
18. Create a short support card from the test, with title, audience, prerequisites, exact checks, expected results, escalation and review date. Label untested steps. Expected: clear user-facing procedure with source . Verify with an actual reviewer or state self-review. Do not convert a synthetic example into a workplace-approved procedure.
19. Optional private test SharePoint publication: only with site-owner approval, place the reviewed card in an isolated support library, grant only the test group and verify an allowed user can read it while an unapproved dummy user cannot. Expected: actual access boundary. Recovery: remove broad permission and retest; if no tenant, keep a local folder and no SharePoint-integration claim.
20. Run offline search again, demonstrate normal/no-match/escalation outcomes, and compare its advice with the source cards. Expected: faithful card retrieval with no generated claims. Verify a person can follow the card in the lab. Recovery: revise wording using actual failure evidence; rerun relevant tests and preserve earlier version. Record any human usefulness result qualitatively; no timed benefit without a baseline.


## I–J. Failure tests and acceptance
Offline: missing card fields, duplicate ids, invalid JSON or blank query → reject with INVALID; unknown topic → NO MATCH; password/admin topic → ESCALATE. Recovery: restore the synthetic template, review the input and rerun. Keyword matching can miss paraphrases and cannot prove security, permissions or diagnosis; do not present it as a production assistant.
Meeting: two-way audio, remote video and dummy screen share must be observed; introduced mute/camera faults must be recovered and retested; ticket must retain true status/owner. A local preview is not remote delivery. Dedicated room-system acceptance additionally needs actual certified device/account/licence, owner procedure and a supervised end-to-end room call; currently absent.
AI extension acceptance, if later approved: freeze a separate synthetic set of answerable, unknown and restricted questions; compare card lookup with model-assisted responses; record source citation correctness, invented instructions, unsafe advice, failures, latency and cost. Reject invented/uncited or permission-crossing answers. No live data or autonomous actions. Keep rules/folder search if AI adds risk without useful measured benefit.
## K. Evidence and cleanup
Keep source/cards/tests, actual outputs, dummy meeting notes, reviewed card, sanitized screenshot if useful and a short demo. Capture operator and assistance. End test call, stop sharing, remove only lab-created content/permissions with owner approval, restore audio/video selections to their recorded original state and disconnect spare equipment safely with supervisor. Remove temporary downloads/logs under agreed retention. Do not delete real recordings or change shared room defaults.
## L–N. Interview, conditional wording and extension
After personally performing it, explain the collaboration need, limited equipment, selected baseline, actual audio/camera fault, own checks, remote validation and remaining room/tenant limits. The value is a testable repeatable readiness process, not a claimed reduction in workplace meeting failures.
Conditional CV wording: “Tested a two-device Teams meeting workflow in a lab, verified audio/video and screen sharing, and documented reversible fault recovery.” Add searchable guide/SharePoint/AI work only for the branch actually completed and evidenced. State assistance when used.
Optional extension: an approved, permission-aware knowledge assistant with source-cited responses and human escalation. Production would need real identity enforcement, content ownership, access tests, monitoring, retention and operational sign-off. No commercial AI capability follows from this guide or an assistant-generated script.

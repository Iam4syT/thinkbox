# Service request workflow lab
## A Purpose and sourced need
Practise a small internal support workflow that makes ownership and changes visible. Staff applications need dependable user support and secure changes, as described in the role advert. A repeated need for this exact tracker inside the employer is a hypothesis, not an inspected problem. Public-service context: https://www.ombudsman.org.uk/our-strategy .
## B Requirement and evidence gap
Targets Power Apps, Power Automate, Dataverse, SharePoint/Teams handover and troubleshooting. Existing M365 support helps define the workflow. It does not prove the missing professional app/flow delivery. This guide and the local implementation are new assisted practice; native Microsoft steps below are unrun.
## C Repeated use and simpler baseline
A support colleague could review a queue daily and correct ownership, duplicates and blocked work. Start with a list and a clear state rule rather than an AI agent. AI text classification is optional only after permissions and rules work; it adds cost and uncertainty to a task with four known statuses. Do not automate complaint decisions or handle real case records.
## D Architecture and boundary
Local Python Workflow -> in-memory synthetic request store -> state and version checks -> JSON snapshot. Caller-supplied actor strings simulate access rules; they are not authenticated identities. Native extension: a canvas Power App -> Dataverse request table -> reviewed notification flow -> private Teams link. SharePoint can host a staff runbook, not duplicate sensitive case data. The local model is not a live connector or full persistence layer.
## E Prerequisites licences and cost
Local path needs Python 3.10 or newer, no third-party packages, credentials or network. Native work needs a separate authorised non-production environment, test identities, an approved DLP policy, and the licences needed for Dataverse, connectors and sharing. Microsoft documentation checked 2 November 2026 warns of developer-environment changes and unmanaged-environment deprecation. Verify current developer-plan eligibility and environment rules before relying on free access. Do not enable managed services, buy licences or create a tenant in this run. Sources https://learn.microsoft.com/en-us/power-platform/developer/plan and https://learn.microsoft.com/en-us/power-platform/alm/solution-concepts-alm . No monetary saving is measured.
## F Local starting state and first run
1. Open a terminal in this project's public root after downloading the project. Check `python3 --version`. Expected Python 3.10 or newer. If absent, install from an approved Python distribution before continuing; no package installation is needed.
2. Run `python3 -B scripts/workflow.py`. Expected one synthetic request with status Triaged and version 2. Check the id is SYN-001 and no personal data appears. If the file is not found, check the working directory contains scripts and tests.
3. Run `python3 -B -m unittest discover -s tests -v`. Expected nine tests. Read any failure before editing code; do not remove a failing assertion just to turn the output green. These check business rules, not authentication or a Microsoft service.
4. Open scripts/workflow.py and explain why a stale version is rejected and why the owner check precedes mutation. Change a synthetic owner or add a new permitted state in a private branch; add an appropriate test. Record your own output. The assistant's earlier run is not your independent evidence.
## G Native sandbox steps that remain unrun
1. With approved sandbox access, select the intended non-production environment in make.powerapps.com. Record its name and region privately. Check it is not Default or production by accident. If access/licensing is uncertain, stop and ask the tenant owner; do not bypass policy.
2. Create an unmanaged solution with a lab publisher and version 1.0.0.0. Within it create Request with primary name Summary; add RequestId text, Owner using Dataverse ownership, and a choice column WorkStatus with New, Triaged, In progress, Resolved. Add a unique alternate key for RequestId and wait for its successful activation. Use only synthetic records. Verify two separate test users have deliberately scoped security roles. A gallery filter is not authorisation.
3. Create a canvas app in the solution using the Request table. Add a gallery, view form and edit form. Set the gallery Items to the table; display Summary and WorkStatus. Connect the form DataSource and Item to the table and selected gallery row. Use a submit button with SubmitForm and OnSuccess to return to the list. Test a required blank Summary and a valid new record. The exact Power Fx names depend on generated table/choice names; inspect the actual schema rather than pasting guessed identifiers.
4. Apply allowed transition validation at a server-enforced boundary for all write paths. A client button alone is not a secure transition policy. For a first supervised exercise, keep transitions in a reviewed server operation or plugin; if that is outside current skill, leave native transition enforcement pending. Verify a direct API request cannot skip the rule before calling this control complete.
5. Add a solution-aware flow on a permitted request change. Keep notifications to synthetic ids and status only. Use connection references, environment variables and trigger conditions so a flow update cannot trigger itself indefinitely. Record run history. Disable the flow if it loops; inspect the trigger/update relationship and retest with one item. Do not post into a real team.
6. Test two identities against Dataverse security: owner can access the allowed row; second user cannot access a row outside their role. Test the table/API as well as the UI. Capture anonymised denial and successful checks. If a maker/admin identity can see everything, it is not a valid least-privilege test identity.
7. Use Dataverse ETags for a concurrent edit exercise. Read the same row twice, update one copy and submit a second stale update using If-Match with its earlier ETag. Expect precondition failure rather than silent overwrite. Refresh, review both changes and retry consciously. Source https://learn.microsoft.com/en-us/power-apps/developer/data-platform/webapi/perform-conditional-operations-using-web-api . This is not supplied as an executed integration.
8. Write a SharePoint test runbook with app owner, support route, known error, rollback contact and synthetic evidence. Optionally link the app in an approved test Teams channel. Confirm users also have the underlying data rights and licences; sharing the app alone does not grant data access.
## H Break and fix
Local duplicate id must fail without adding a row. A wrong actor must raise PermissionError without changing version. A stale version must fail after an earlier successful move; refresh the snapshot and retry with the new version. A New-to-Resolved skip must fail. In the native sandbox, revoke one approved test permission, capture denial and restore only the approved role; do not broaden access to fix a test.
## I Acceptance tests
Local acceptance is nine tests with no failures plus review of source limits. Native acceptance is separate: creation, duplicate prevention, server-side transition enforcement, two-user security, stale-update denial, one bounded flow run and runbook review. No native acceptance passes until observed outputs are captured. Baseline and candidate timings, user savings and cloud cost remain unmeasured.
## J Cleanup and recovery
The local model is in memory and exits without persistent data. Remove only generated local evidence you no longer need. For the sandbox, disable the flow, export the learning solution and evidence, then delete only the explicitly named lab records/app/solution with the owner's approval. An unmanaged solution deletion does not automatically remove its components; inspect the component dependencies and delete only lab components. Do not delete an environment containing other work.

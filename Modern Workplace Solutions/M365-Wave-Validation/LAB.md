# Lab 1 — Microsoft 365 migration-wave validation and handover
## A. Outcome and honest state
Prepare a small, repeatable evidence pack showing whether a pilot workplace change meets agreed identity, licensing, content, access, mail-flow and support checks. Offline checker implemented and fixture-tested by the assistant; tenant workflow unrun. It does not migrate mailboxes or certify migration readiness. the learner must run and explain it before describing personal completion.
## B. a Microsoft cloud consultancy context and business problem
a Microsoft cloud consultancy publishes tenant-separation consultancy and a financial-services separation case study. Those establish service relevance; performance and scale are employer claims. Scenario inference: a consulting team needs consistent pilot evidence before approving change. The lab uses fictitious ResearchCo and six users, not a real a Microsoft cloud consultancy customer. No internal architecture or incident is inferred. Primary context: https://www.applicable.com/consultancy/ and https://www.applicable.com/knowledge-hub/1892-2/ ; technical guidance https://learn.microsoft.com/en-us/sharepoint/turn-external-sharing-on-or-off and https://learn.microsoft.com/en-us/microsoft-365/migration/cross-tenant-mailbox-migration?view=o365-worldwide .
## C. Requirement mapping
Role skills: M365 service configuration, identity, migration support, testing/cutover assistance, early-life support, clear customer handover. Small manual SharePoint content transfer exercises checks; it is not an Exchange tenant-to-tenant migration.
## D. Gap mapping
Strengthens formal test/handover methods and transfer validation beyond existing scoped user migration. Identity and mail-flow support are already professional strengths. Does not establish enterprise migration lead or Purview legal-case capability.
## E. Repeated-use value and baseline
Use for every pilot wave and daily hypercare review. User: associate consultant and senior reviewer. Friction: missing validation evidence or unnamed support owner. Baseline: six-item manual checklist. Success target: fail/unknown inputs never treated as complete, all evidence links accounted for. No observed client saving. AI is unnecessary in core decisions; optional drafting of redacted handover notes must preserve source links and human review.
## F. Architecture
Synthetic user roster -> test tenant/source and target SharePoint sites -> user access and content checks -> local JSON flags -> report -> human approval and operational handover. Boundaries: administrator creates configuration; ordinary test users prove access; no production data, tenant secrets or automated cutover. Each flag references a dated check in private evidence, not a screenshot alone.
## G. Prerequisites, time and cost
Offline lane: Python 3.10+, a local copy of public/ and terminal; no accounts/packages; £0. Planned budget: one to two focused weekends, not measured duration.
Tenant lane: an explicitly authorised disposable M365 tenant, SharePoint-capable licences for two test users, Teams/Exchange licences if checking those workloads, SharePoint/User administration roles, and a separate ordinary-user browser session. Developer access/trials are not guaranteed; check live pricing and billing before purchase. No tenant change performed in this run. Lower-cost option: stop after offline checks and state the reduced scope. No real cross-tenant migration licence required for this manual site-copy lab; Exchange migration is an optional separately licensed extension.
## H. End-to-end steps
### Step 1 — Establish scope
Start: no tenant changes. Action: create a private scope note naming the disposable tenant, six dummy users, two sites, authorised admin, reviewer and support owner. Record source/target URLs and the evidence directory. Set a stop rule: no customer data, no change outside these sites. Expected: one bounded scope sheet. Verify: reviewer confirms object names and licences. Recovery: if access or approval missing, use offline lane only.
### Step 2 — Run the local baseline
Start: in the public project folder. Action: run python3 --version, then python3 scripts/check.py templates/sample.json. Expected: CHECKS_PASS and exit 0 from fabricated flags. Verify: compare fields with scripts/check.py RULES; record that evidence/sample-output.json is synthetic, not a tenant result. Recovery: Python missing -> obtain an approved Python runtime; wrong directory -> locate scripts/check.py before rerunning. Do not label synthetic CHECKS_PASS as cutover approval.
### Step 3 — Check refusal behaviour
Action: run python3 scripts/check.py templates/failure.json. Expected: HOLD with identity_verified false and exit 1. Copy sample.json to local-evidence.json, remove one required field and run the checker on that file. Expected: REVIEW; change a boolean to the string true and rerun. Expected: INVALID and exit 2. Verify: no case falsely passes. Recovery: restore the copied sample; never rewrite failure evidence as success.
### Step 4 — Create isolated users
Start: authorised test tenant only. Action: in Microsoft 365 admin centre > Users > Active users > Add a user, create pilot.reader and pilot.owner with the tenant's onmicrosoft.com suffix. Assign only purchased/test workload licences; save passwords in a private manager. Sign each user into its own session and record sign-in result. Expected: accounts access licensed workloads. Verify: no admin role on reader; identify each user's exact object in scope sheet. Recovery: review assigned licence/service plans or sign-in logs; do not grant blanket admin rights.
### Step 5 — Configure source and target sites
Action: SharePoint admin centre > Active sites > Create > Team site, create Research-Pilot-Source and Research-Pilot-Target; choose owner pilot.owner. Record site URLs. In target site's permissions grant pilot.reader Read through Visitors; leave an unrelated dummy user uninvited. In sharing settings keep external sharing disabled for this lab site; do not relax tenant-wide defaults. Expected: intended reader can read and unrelated user cannot access. Verify: test both ordinary-user sessions. Recovery: inspect direct access, site group membership and link scope; remove accidentally broad links before retesting.
### Step 6 — Seed source content and inventory
Action: create three harmless files locally: welcome.txt, instructions.txt and schedule.csv. Upload to source Documents using pilot.owner. Download copies, calculate SHA-256 using Python hashlib or an approved file tool, and record filename/size/hash in inventory.csv. Expected: three source items and recoverable copies. Verify: reopen each file and count CSV rows. Recovery: filename collision -> use a clean named folder; wrong content -> replace only synthetic files and recapture the manifest.
### Step 7 — Execute the small transfer
Action: download source files with pilot.owner, upload them to target Documents in a Pilot-Wave-01 folder, preserving exact names. Record start/end dates only if actually measured; check file count, size and hashes after download from target. Expected: three identical contents. Verify: SHA-256 equality and reader access. Recovery: mismatch -> stop the wave, locate the differing file and retry that item; never tick content_verified until the mismatch is explained. This method does not preserve complete version history, original metadata, permissions or audit history; record those limits.
### Step 8 — Validate the workplace dependencies
Action: using licensed test accounts, send a harmless pilot-owner to pilot-reader email and reply; record receipt and use Exchange admin centre message trace if delayed. Open Teams with pilot.reader and test an ordinary chat only if licensed. Record expected SharePoint links and user instructions. Expected: agreed collaboration paths work. Verify: recipient confirms receipt and links; distinguish mail content from Exchange migration. Recovery: missing licence -> hold licensing check; mail delay -> check trace and domain evidence, without changing production DNS.
### Step 9 — Complete checks from observed evidence
Action: fill local-evidence.json using actual test records. Set a field true only after the named test passes. Missing/unknown evidence stays omitted -> REVIEW. Map identity_verified to ordinary sign-in; licensing_verified to plans; content_verified to hash comparison; access_verified to allowed/denied checks; mailflow_verified to message receipt; support_owner_verified to named handover acceptance. Expected: a defensible report. Verify: reviewer traces every true value to one source. Recovery: unverifiable field -> remove it and keep REVIEW.
### Step 10 — Practise the content failure
Action: alter one target file's harmless text, download and hash again. Expected: hash mismatch; set content_verified false -> HOLD. Compare with retained source, replace the one target copy and rehash. Verify: matching hash and original failure retained. Recovery: if unsure about source integrity, halt and rebuild from known fixture; do not overwrite the evidence ledger.
### Step 11 — Practise the permission failure
Action: remove pilot.reader from target Visitors, test its access, and record denial. Expected: intended reader fails, access_verified false. Restore only Visitors Read and retest; also retest unrelated user denial. Expected: access correct both ways. Recovery: direct shares override intended groups -> inspect Manage access and remove lab-only direct share. Never use Anyone links as a fix.
### Step 12 — Handover and early-life support
Action: prepare handover.md with object list, change scope, tests/links, remaining limits, known issues, escalation contact, rollback boundary and next review. Write a short user note explaining the new URL and where to get help. Simulate one reader incident and record triage/decision/escalation. Expected: reviewer can locate every result and support owner. Verify: reviewer signs off only the lab scope. Recovery: unclear ownership -> support_owner_verified false; no cutover authority inferred.
### Step 13 — Clean up and verify
Action: export sanitised evidence first. Delete only both named test sites and dummy users after lab owner confirmation, using admin-centre recovery controls; remove locally downloaded dummy copies when no longer needed. Review recycle-bin retention and licence assignments, and cancel any purchased trial only through its authorised account process. Expected: active lab objects removed, no ongoing unwanted bill. Verify: active-sites/user lists and billing owner confirmation. Recovery: wrong deletion -> use product recovery; stop and seek tenant owner help. Never delete a real site's objects.
## I. Break/fix record
Use steps 10–11 and missing-evidence step 3. Capture symptom, hypothesis, own check, fix, retest and escalation threshold. A missing record is an unknown; it is not evidence the service passed.
## J. Acceptance
Offline fixture tests pass; false flag holds; missing field reviews; invalid type rejects. Tenant acceptance requires intended reader allowed, outsider denied, three target hashes match source, licensed mail test confirmed and signed handover. All tenant criteria remain unrun. A senior consultant decides real cutover readiness after full design/security review.
## K. Artefacts
README, LAB, architecture, source, fixtures, test output, sanitised inventory, allowed/denied screenshots, failure/recovery log, reviewer handover, short demo. Never publish user UPNs, tenant IDs, private URLs, licences, contact details or mail content.
## L. Interview story
Explain need for repeatable wave checks; constraints; why manual pilot plus offline checks; own transfer/permission choices; one failed check and recovery; observed acceptance; limits of manual metadata/version handling. Only speak in past tense after personal completion.
## M. Conditional wording
Use only after the learner completes and evidences it: “Built a test-tenant migration validation pack, checking content integrity, user access and handover evidence; documented a failed check and verified recovery.” Do not call it enterprise tenant migration.
## N. Optional extension
A real cross-tenant mailbox lab needs two tenants, scoped source migration group, MailUser attributes, Exchange roles and paid per-user Cross-Tenant User Data Migration licences. Holds can block moves and a successful move removes the source mailbox. Follow the current Microsoft cross-tenant migration guide and an explicitly reviewed rollback plan; do not treat manual file copy as this extension. AI extension: draft a summary from redacted approved notes, compare against a manually written baseline for omissions and unsupported claims; no autonomous permissions or cutover decisions.

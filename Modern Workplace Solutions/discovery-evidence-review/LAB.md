# Lab 2 Retention and discovery evidence review
## Purpose and job link
Build a synthetic investigation record that selects in-scope dummy items and creates a hashed manifest without deleting or changing source files. DWP advert requires eDiscovery, retention, litigation hold and governance. The recurring need is to demonstrate what was searched, selected and handed over. This is a learning scenario; no actual DWP legal matter is asserted. Strengthens precise scope, documentation and evidence-handling checks.
## Baseline architecture and costs
Baseline: manually compare item subjects and scope, then list files. Proposed deterministic filter and SHA-256 manifest make the procedure repeatable. They do not prove legal admissibility, enforce preservation or simulate the full Purview index. AI is unnecessary for an exact synthetic token search; an AI summariser would add disclosure and accuracy risks without a tested benefit here. Stack: Python 3, synthetic JSON, scope list and hashed output. Flow: permitted dummy corpus → scoped filter → manifest → human review. Offline cost: no additional purchase. Native extension needs test mailboxes, suitable Purview retention/eDiscovery licences, least-privilege roles and a separate authorised lab tenant. Check current licence entitlement; do not buy trials without authorisation. Plan one focused weekend plus service propagation time.
## Granular offline steps
1. Read fixtures/sample.json: three synthetic items, two allowed mailboxes and one out-of-scope mailbox. Target token is DEMO-CASE-17. Manually record which items should match both mailbox and token.
2. Run python3 scripts/review.py fixtures/sample.json > evidence/manifest.json. Expected: only the in-scope matching item is selected; a matching item outside allowed scope is excluded. Source data is unchanged.
3. Inspect each output item ID and hash. Independently calculate SHA-256 of its canonical JSON with sorted keys and compare. Hash confirms bytes represented by the chosen serialization, not legal truth or original server preservation.
4. Run python3 -m unittest discover -s tests -v. Expected: correct selection, case-insensitive token matching, scope exclusion, duplicate rejection and required-field validation all pass. Record actual counts.
5. Copy the fixture to fixtures/broken.json and add an unapproved mailbox to a test item, without adding it to allowed_mailboxes. Expected: exclusion remains. Do not change allowed scope to make a desired result pass.
6. Remove the required query token and run again. Expected: explicit failure rather than a healthy zero-match result. Restore token; verify correct result.
7. Change one selected dummy subject and rerun. Expected: the hash changes if the item still matches. Compare outputs and explain why a hash cannot tell whether evidence is accurate.
8. Prepare a review record with purpose, request owner, allowed mailboxes, token, search date, output count, rejected items and outstanding checks. Label it synthetic and keep policy decision ownership with the authorised owner.
## Native Purview extension unrun
9. Read the current Purview eDiscovery experience documentation and verify entitlements and least-privilege case access. Classic eDiscovery instructions were retired outside the stated exceptions; do not follow old Premium/Standard navigation blindly.
10. Create two disposable test mailboxes and dummy messages only under separate live-lab authorisation. Include DEMO-CASE-17 in two subjects, plus a control message. Record mailbox and subject privately.
11. At purview.microsoft.com, open Data Lifecycle Management and the retention-policy workflow supported by your tenant. Create a uniquely named LAB-only static Exchange policy scoped solely to the two disposable mailboxes, using retain-only behaviour and an agreed test duration. Do not use deletion, adaptive organisation-wide scope or Preservation Lock. Review scope and save only under authorised lab scope.
12. Record policy distribution status. Wait for documented propagation; a saved policy is not proof retention has taken effect. Inspect the policy’s inclusion list and any applicable retention conflict. Keep this check distinct from eDiscovery hold.
13. Open the current eDiscovery solution → Cases and create a uniquely named LAB case. Add the permitted case member, then create a search scoped to the disposable mailbox sources with the target subject/token condition. Use the current search builder; document generated query and scope.
14. Run the search and examine statistics and samples. Compare expected dummy hits with actual output. If none appear, first check permission, mailbox source, token, indexing/process state and dates. Do not broaden to all mailboxes to hide failure.
15. If a hold exercise is authorised and licensed, create a hold restricted to the dummy case sources and inspect its status. Explain that a retention policy, eDiscovery hold and litigation hold serve different purposes; this lab does not prove every hold behaviour.
16. Export only the approved dummy search output if your licence/role permits it. Save the native export report privately; create a sanitised local manifest and verify count/hash handling. A local manifest is not a replacement for native audit/export metadata.
## Acceptance failure recovery and cleanup
Offline acceptance: known matching item selected, out-of-scope item excluded, missing query/data rejected, duplicate IDs rejected and changed content gives a changed hash. Native acceptance: source scope, membership, licence, policy distribution and search results verified; any hold/export remains separately evidenced. Record denied permissions, propagation delays and omitted/partially indexed items. For cleanup, first confirm no real legal or organisational retention applies; only then remove authorised LAB-only objects after evidence review. Never release an actual legal hold or purge real content. Keep source fixtures and audit notes; remove generated dummy outputs only when no longer needed.

# Lab 1: Customer ticket handover and safe escalation
## A. Outcome and status
Build a small offline tool that finds missing handover details and proposes a queue order for one synthetic customer. A person still confirms priority and every change. This is an independent learning scenario, not Elevate's internal platform. Python code can be tested locally; Microsoft 365 and real service-desk work remain unrun.
## B. Company need and research
Elevate's Support Analyst advert combines multiple-customer support, service-level targets, updates, escalation and documentation. Its Microsoft 365 article describes reviewing customer settings and helping users get more value from the platform. Scenario hypothesis: a consistent handover could help analysts avoid repeating basic questions. No observed Elevate defect, incident volume or time saving is claimed.
Sources checked 7 November 2026: https://elevate-cloud.co.uk/careers/support-analyst ; https://elevate-cloud.co.uk/insights/unlocking-microsoft-365-full-potential .
## C–E. Requirements, gaps and repeat use
Exercises ticket logging, workload decisions, cloud support, customer updates, escalation and knowledge notes. Builds on professional M365/case work; introduces explicit customer-data separation and input checks. A support analyst could use the checklist at each handover and daily queue review. This recurring use is plausible, not validated customer demand.
Baseline: read every sample manually and record priority/owner/next update in a note. Success target: expected order and missing fields agree with a written reference; no other customer's records appear. Measure personal review time only when actually run. Start with a 90-minute local slice; allow a separate 2–3-hour authorised tenant session.
## F. Architecture and AI decision
Synthetic JSON tickets → strict schema check → selected-customer filter → deterministic rules → human-readable JSON handover. There is no login, API, mail sending, tenant change or secret. Customer filtering is a demonstration of boundaries, not production access control. A real service needs authenticated server-side authorisation, audit logs and security review.
AI baseline comparison: fixed rules are cheaper and easier to inspect for this small structured task. Do not add an LLM. A later summariser would need redaction, permission checks, a held-out test set and evidence of benefit over a template before use.

Use Python 3.10 or later, a text editor and a terminal. The standard library needs no package download. Local cost is £0 using an existing computer. ## H. Step-by-step local build and operation
1. Starting state: a terminal and the project files. Navigate to this scenario folder. On macOS/Linux run `python3 --version`; on Windows run `py --version`. Expect 3.10 or newer. If Python is missing, use the official installer and reopen the terminal; do not paste commands into the Python prompt.
2. Open `sample.json` in the editor. It has three fake tickets: two for north-demo and one for south-demo. Read the meaning of impact (1 low to 3 high), urgent and security flags. JSON uses lowercase true/false. Do not enter real names, passwords or ticket text. If parsing fails, compare commas and quotes with the original file.
3. Before running the code, write your expected north-demo result: T1 first as P1; T2 P3 with owner and next_update missing; T3 absent. This manual answer is the baseline. Keep it in a private note and compare after the run.
4. Run `python3 review.py sample.json north-demo` (Windows: replace python3 with py). Expect two results, T1 then T2, both requiring human review. Check every id and missing-field list against step 3. If the command cannot find the file, check the current folder; do not change system paths.
5. Run `python3 review.py sample.json south-demo`. Expect only T3 with security escalation. Treat a suspected security issue as requiring the security process, not an automated conclusion that a breach occurred. Check that no north-demo record appears.
6. Run `python3 -m unittest -v`. Expect ten tests to pass. They check isolation, priority, missing handover, duplicates, bad input and unchanged source data. A pass establishes only these synthetic behaviours. If a test fails, keep its output, correct the code/input and rerun the affected suite.
7. Create `broken.json` by copying the sample in the editor. Change the first security value from false to the string "false". Run `python3 review.py broken.json north-demo`. Expect exit code 2 and a boolean validation error, with no output handover. Fix the value and repeat; do not coerce untrusted text to a truth value.
8. Clear T1's next_update in the copy and run it again. Expect the missing field to be listed while priority remains P1. Add a proposed update time after considering the service agreement. The software only checks presence; it does not validate time zones, deadlines or whether the proposed time was agreed.
9. Write an operational note: symptom, impact, checks made, evidence, current owner, next update and escalation reason. Use only fake facts. The sample does not send the note or update a real ticket. Ask another reader to say which task comes next and why.
### Optional M365 observation — unrun
10. Only in an authorised personal test tenant, sign in to `https://admin.microsoft.com`. Confirm the tenant name before proceeding. Go to Health → Service health. A suitable read role is required; use the least access needed. If denied, request the appropriate test role rather than broadening permissions yourself. Read https://learn.microsoft.com/en-us/microsoft-365/enterprise/view-service-health for the current route.
11. Choose Exchange Online, Teams or SharePoint Online and record whether the page shows a relevant advisory or issue. If none appears, record none observed; do not invent an outage. In a synthetic ticket, distinguish the observed service status from a user's separate local symptom. Never copy customer identifiers into the public repository.
12. In your note, give a plain-language update and the next check. A tenant advisory does not prove it caused this user's fault. Do not reset passwords, change access or close a real case. Have an experienced engineer review any proposed diagnosis before real use.
## I–J. Break/fix and acceptance
Accept the local slice only when ten tests pass, each customer query contains only that customer's records, bad input exits without a handover and the source file stays unchanged. Add an unseen synthetic ticket and explain its priority without looking at the implementation. Duplicate an id within the same customer and expect rejection; repair it and rerun. Cross-customer duplicated ids are permitted because customer plus id is the key. For a real service, filtering alone is insufficient and authentication must be tested separately.

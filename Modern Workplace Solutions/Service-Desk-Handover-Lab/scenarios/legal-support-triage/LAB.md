# Legal document and meeting support lab

## A Outcome and present state
Create a small support queue and troubleshooting record for a document-access fault, meeting fault, VPN fault and printer request. The local routing tool is built and assistant-tested. Real Teams, Zoom, legal applications, printer, AV and VPN steps are unrun. No rule automatically closes a ticket or changes a service.

## B Company problem and C Job mapping
A purpose-led law firm asks its analyst to support legal document workflows, meeting rooms, remote access, vendors and agreed service times. Hypothesis: a clear fault record and retest checklist could help colleagues continue their work and help specialists receive useful evidence. The firm has not confirmed a specific incident, document system, VPN product, printer model or response target. The lab uses ordinary Office/SharePoint and Teams as practice; these do not prove support for an in-house legal application.
This solution covers support, priority, SLA checks, escalation, vendor liaison, documentation and user retesting. An SLA is an agreed service target. The 30-minute sample target is invented test data, not a A purpose-led law firm SLA.

## D Candidate gaps and E Repeat use
Professional Microsoft 365 diagnosis, FirstBank ticket coordination and escalation are the starting strengths. Legal-document tools, room hardware, Zoom, VPN administration and printer handling need new evidence. A service desk could use the record daily, but actual company demand and time saved remain unmeasured. Baseline: a human routes the same five synthetic tickets using the written decision order. Compare tool results with that independent answer sheet. AI is unnecessary for these few fixed rules; it should not receive confidential matter content or decide who gets access.

## F Design and G Prerequisites
Data flow: synthetic symptom and impact → local CSV → rule explanation → analyst review → approved checks → user retest → closure decision. Security suspicion comes first, then possible shared outage, elapsed target, urgent event and normal first-line work. A test user's successful retry is a closure prompt, not proof of manager approval or incident resolution.
The free local part needs Python 3.10 or later and a text editor. Online practice needs an authorised Microsoft 365 test tenant with SharePoint/Office and Teams access, two test accounts, separate browser profiles and optionally two consenting test participants. Some subscriptions require Teams separately. Verify entitlement before buying or enabling anything. Room AV, a printer and a VPN gateway need separately authorised lab hardware/software; without them, record those steps as tabletop practice. Use no real legal matter or personal data. Budget 1–2 hours offline and another weekend for the online cases; actual duration has not been measured.

## H Part 1 Run and challenge the local queue
1. Open `data/tickets.csv`. Read the headers: id, kind, suspected_exposure, service_wide, urgent_event, minutes_open, target_minutes and user_retested. Expected: five synthetic records. Verify no real people, matter names or client documents appear.
2. Before running code, write your expected route for each row using the rule order above. Expected: a manual baseline answer sheet. Keep it unchanged when you later compare; do not tune the baseline to fit the program.
3. Run `python3 scripts/triage.py data/tickets.csv`. Expected routes: LAB-T01 FIRST LINE; LAB-T02 URGENT REVIEW; LAB-T03 SECURITY; LAB-T04 INCIDENT; LAB-T05 ESCALATE. The first four show KEEP OPEN; T05 shows CONFIRM. Compare every route and explain why CONFIRM still needs a human decision.
4. Run `python3 -m unittest discover -s tests -v`. Expected: eight passing checks, including the exact elapsed-target boundary and security precedence. Record actual output. A failure must be investigated before using the tool.
5. Copy the CSV to `data/my-tickets.csv`. Change T01 minutes_open to -1. Expected: REVIEW with Invalid time or target; no normal route. Restore it. Remove a required column from another copy. Expected: non-zero error and no routing decision. This tests broken exports and stops false reassurance.
6. Set T02 suspected_exposure=yes and service_wide=yes. Expected: SECURITY, even though it is an urgent meeting. Restore the sample. Record the conflict and explain why confidentiality takes priority over convenience. Do not put real confidential content into a failure exercise.

## H Part 2 Build the support record
7. Create `my-support-log.md` with ticket ID, affected test user, service, symptom, time reported, impact, scope, approved priority, next update, checks, findings, actions, escalation owner, retest and closure. Expected: a usable blank record. Use relative test times unless you actually measure time; never invent an incident timestamp.
8. Write a synthetic request: “Alex cannot open Demo Matter 001 before a meeting.” Ask whether one user or several are affected, whether the browser works, what changed and the next deadline. Expected: an impact/scope note. If the question is unanswered, record unknown rather than declaring a widespread outage.
9. Read the tenant's service-health page through the authorised admin account. Expected: observed service state with check time, or access unavailable. Match any advisory to the symptom before using it as a cause. An empty advisory list is not proof that a local fault is impossible.

## H Part 3 Test document access with a safe substitute
10. In the authorised test SharePoint site, create a library or folder named Demo Matter 001 and upload a harmless Word file saying “Practice document only”. Share it with Alex using Specific people; leave Jordan uninvited. Expected: a named-user share. Verify the permission list and exact recipients; do not choose Anyone as a quick fix.
11. In Alex's separate browser profile, open the file, edit one sentence, save and reopen. Expected: authorised access and retained edit. In Jordan's profile, try the same URL. Expected: access denied or an access request. Save redacted evidence of both. If Jordan can open it, inspect inherited site membership and links before changing anything; record this as an access-control failure.
12. Introduce the fault by removing only Alex's test-specific permission, keeping the site's administrator intact. Expected: Alex is denied after sign-out/retry and normal propagation. Check permission inheritance and existing links if access persists; do not assume a removal took effect immediately.
13. Diagnose with the support record: confirm the signed-in account, copy the exact error, compare browser and desktop access if a licensed desktop app is available, and inspect the permitted file access list. Expected: the evidence points to an access change only if those checks support it. Do not delete profiles or clear all credentials before basic checks.
14. Restore the approved specific-person permission for Alex. Ask Alex to retry the original action, save and reopen the file. Expected: access and save restored for Alex while Jordan remains denied. Record both results and the approval basis. Do not state that restoring permission fixes every document fault.
15. Record a separate legal-tool escalation example: unknown document-production add-in fails. Collect product/version, harmless error text, reproduction steps, affected scope and deadline. Expected: a useful specialist handoff. Do not install an unknown add-in or claim that SharePoint is the firm's legal system.

## H Part 4 Test meetings and explain room boundaries
16. In the test Teams account, create a short meeting with a consenting second test participant. Join using the approved app or browser. Expected: both participants can join. Record account type and app/browser version. No recording or transcript is needed.
17. Use Teams Settings → Devices to choose the intended microphone, speaker and camera. If a test-call option exists, run it; otherwise have the other participant confirm audio both ways. Expected: a recorded functional result, not simply a device appearing in a list. If unavailable, check the browser/OS permission and device selection before changing drivers.
18. Mute the test microphone or select a wrong test input deliberately. Expected: the other person cannot hear the test speech. Check mute, selected input, OS permission and another permitted app to isolate the layer. Restore the original input and retest both directions. Record what actually fixed the issue. Do not assert a network cause from silence alone.
19. With separately authorised room equipment, check screen input, supported display cable, dock power, camera and speaker selection, then join a test meeting and share a harmless screen. Expected: the remote test user confirms sound and picture. If there is no room kit, document a labelled tabletop checklist only. A Teams web call does not demonstrate AV hardware support.
20. If licensed Zoom access is available, repeat the audio/video checks in Zoom and record its actual version and results. Otherwise keep Zoom unrun. Teams experience cannot be copied into a claim of Zoom proficiency.

## H Part 5 Network printer and vendor boundaries
21. On a permitted Windows test device, use Settings → Network and internet to check the active connection. Run `ipconfig /all` and `Resolve-DnsName example.com` in PowerShell. Expected: local addressing information and a DNS result if that network permits it. Keep IP details private. A DNS answer does not prove the VPN or application is healthy; an ICMP failure alone does not prove an outage.
22. For an approved lab VPN only, record its product, supported configuration and access owner. Compare an approved test endpoint before and after connection, check route/DNS behaviour and capture the VPN error when deliberately disconnected. Expected: observed access follows the documented lab design. No VPN product or gateway is supplied here, so current status is unrun. Do not change a work VPN, firewall or security setting.
23. With an authorised test printer, check power, paper, network connection and the Windows queue; send a harmless test page and confirm physical output. Pause only your own test queue/job to reproduce a waiting job, then resume and retry. Expected: printout and queue state agree. Without hardware this is a tabletop plan, not printer-maintenance experience. Escalate electrical faults, hardware repair or unapproved driver installs.
24. Prepare an unsent vendor handoff: synthetic ticket ID, affected service, impact/deadline, approved priority, product/version, checked steps, safe error text, permitted logs and a clear next question. Expected: a specialist could continue without repeating every check. Redact names, matter content, tokens and private network details. Keep it local; no vendor message is authorised by this lab.

## I Failures and J Acceptance
25. Replay the security, shared outage, time-boundary, urgent meeting and malformed-time cases. Expected: the relevant route remains stable and every unconfirmed ticket stays open. A human may override a route with a written reason. Targets and priority rules must be replaced with actual agreed policy before any real use.
26. Acceptance: eight offline tests pass; all five fixture routes match the independent manual answer sheet; invalid schema fails; security wins a conflicting-priority case; no automatic close or external side effect occurs. Online acceptance separately requires the positive and negative document-access tests and a two-way audio retest. Current build does not establish these online outcomes.

## Cleanup and K Evidence

Remove only your test VPN profile if its owner approves. Verify no broad share, recording or exposed link remains. Keep redacted run logs, original samples, architecture and failure/fix evidence.

# Lab 2 — Support-ticket evidence and escalation desk
## A. Outcome and status
Build a small offline ticket-quality checker and use it alongside an M365 support runbook. A synthetic ticket gets a clear checklist of missing handover information, with a security escalation flag when explicitly marked as a suspected security incident. The portable checker is assistant-built; personal tenant diagnosis remains unrun. It does not connect to an example defence engineering organisation, determine access or close tickets.
## B. Company context and C. Requirements
The vacancy calls for ticket updates, follow-through, documentation, professional help and escalation (see sources below). In an engineering organisation, useful support records plausibly help specialists continue investigation. No an example defence engineering organisation ticketing platform or weak documentation is assumed. Exercise M365/account diagnosis, impact assessment, ticket updates and specialist handover.
## D. Gaps and E. Repeated-use value
Build on Proven case handling and M365 support, while developing structured verification and reviewable tool evidence. Exact password-reset procedure remains Not Yet Evidenced until personally practised. Every escalated case or closure needs enough context for the next person: daily recurring use. The checker only enforces record completeness, not correctness, priority or safety of the technical diagnosis.
## F. Architecture and AI comparison
Synthetic ticket JSON → deterministic local field checks → missing-field report and explicit security flag → human review. Manual template is the baseline. No external API, tenant credential, model or customer data is required. A future AI summary could improve prose but could omit impact, invent a fix or expose sensitive data. Keep rules as the baseline and test factual consistency on synthetic cases before considering AI. AI must never authorise a reset or judge a security incident resolved.
## G. Prerequisites, costs and data
Python 3 and a local terminal; standard-library code requires no paid services. Use sample data only for local tests. For the optional tenant exercise, obtain a separate authorised test tenant, suitable Microsoft 365 licence, two synthetic non-privileged users, a test mailbox and least-privileged admin role appropriate to the task. Availability/licence cost is not assumed. MFA and administrator separation remain enabled. No live tenant work is authorised by this guide. Planned effort: one weekend for records plus one for tenant practice, not measured.
## H1. Establish the manual and portable baselines
1. Starting state: project folder obtained, no credentials configured. Read README and open `templates/complete.json`. Identify the seven fields: impact, symptoms, checks, result, next_owner, next_action, user_update. Expected: each field is understandable without code. Verify that result says what is currently observed rather than claiming every fault is resolved. If a field is unclear, write a manual example first.
2. Open a terminal in the project root and run `python3 scripts/check_ticket.py templates/complete.json`. Expected: COMPLETE and ROUTINE REVIEW. Verify output lists no real user details. If a path fails, check your current folder and filename rather than editing environment-wide paths. Use a valid Python 3 runtime.
3. Run the same command with `templates/incomplete.json`. Expected: INCOMPLETE and missing fields listed, plus SECURITY ESCALATION when the explicit boolean flag is true. Verify that it does not suggest a password reset or mark the case solved. If different, record the defect and review source/tests before using it as evidence.
4. Create a private synthetic ticket describing one user unable to receive mail: one test user, start time unknown, no attachments or live addresses. Fill impact and symptoms; leave unknown checks/results blank. Expected: incomplete report. Verify blanks remain missing rather than being filled with a plausible diagnosis. Recovery: restore from the template if the JSON syntax fails.
## H2. Practise support reasoning without a tenant
5. On paper, distinguish “cannot sign in”, “can sign in but cannot receive mail” and “all users affected”. Write one next diagnostic question for each. Expected: different branches based on symptoms. Verify you are not resetting a password for an unrelated mail-delivery issue. If uncertain, use Microsoft guidance and the support boundary rather than guessing.
6. Add proposed checks to the synthetic ticket with the prefix “planned”: confirm identity through approved procedure, confirm scope/impact, check service status, inspect relevant account/licence/mailbox state, then trace a synthetic test message if authorised. Expected: a plan clearly separate from performed work. Verify no planned action is recorded as a result. Recover by relabelling any ambiguous completed wording.
7. Write a short user update: “I’m checking whether this is an account or mail-delivery issue. I’ll keep you updated and involve the relevant specialist if further access is needed.” Expected: clear next step without a fabricated deadline or result. Verify the language matches what you can actually do.
## H3. Optional authorised M365 tenant exercise — unrun
8. Confirm isolated test-tenant ownership, licence, test-domain control, scope and rollback with the authorised administrator. Create/identify two synthetic standard users through the approved tenant process. Expected: test identities only, no production data. Verify sign-in to the intended tenant before each admin action. If a licence or test mailbox is unavailable, stop the tenant branch and keep only offline evidence.
9. As the ordinary test user, sign in and send a harmless test email to the other test mailbox. Record sender/recipient aliases privately, message subject with LAB prefix and observed delivery. Expected: a baseline mail flow. Verify receipt in the second mailbox and distinguish Junk from Inbox. If it fails, retain the failed baseline and diagnose before introducing another change.
10. Use an authorised admin role to inspect the relevant service-health and user/licence information in the Microsoft 365 admin centre. For a mail issue, use the approved Exchange message-trace interface and the synthetic sender/recipient/time window. Expected: a trace or explicit “no matching event” result. Verify the time range and account rather than inventing an error. If your role cannot access trace, record access denied and escalate; do not grant yourself roles.
11. Practise a password reset only for the standard synthetic user, with explicit permission. Follow Microsoft Entra Users → All users → chosen test user → Reset password and the current guidance (see sources below). Verify the account is not privileged or synchronised from a different authority; follow that authority’s approved route if applicable. Deliver the temporary secret through the permitted channel, never ticket text or screenshots. Expected: authorised reset and secure first sign-in/change, where configured. If the option is unavailable, document the reason and seek the administrator; do not weaken MFA or identity checks.
12. Sign in as the test user using the approved reset flow and repeat the relevant user task. Expected: observed account access or a truthful unresolved failure. Verify a reset has not been mistaken for restored mail delivery; test mail separately. Update only the checks actually performed and the precise result. If a new MFA or mailbox issue appears, retain it and route to the appropriate owner.
## H4. Complete the handover and run review
13. Replace planned checks with performed checks only where evidence exists. Set result to the current observation; set next_owner and next_action to a real agreed role/task, or explicit pending review. Add the last user update. Run the checker on the private record. Expected: COMPLETE if all required fields contain text. Verify that a technically wrong but complete ticket can still pass: human review is mandatory and completeness is not resolution.
14. Create a suspected-security synthetic case with `security_incident: true`; do not copy real security details. Expected: SECURITY ESCALATION regardless of completeness. Verify it cannot be overridden by writing “resolved” in result. Follow the organisation’s security route in real work; no classifier is trusted to clear an incident. If the flag is missing, the program requires review rather than silently treating it as false.
15. Ask a mentor to reconstruct the case from the note: what happened, what was tested, current state, owner and next action. Expected: understandable continuity. Record reviewer feedback or self-review status. If information is ambiguous, revise and rerun, preserving both versions. No measured handover-time saving without a baseline and timed method.
## I. Break/fix and J. Acceptance
Remove next_owner: INCOMPLETE. Set checks to an empty list: invalid-input error. Omit security_incident or set it to the string “false”: invalid-input error rather than a silent routine decision. Set explicit true: SECURITY ESCALATION, even on a complete record. Add unexpected personal fields: rejected by the strict schema. Recover by restoring a synthetic template and rerunning. No fault injection into actual user accounts.
Acceptance: seven text fields validated; security flag required and boolean; unknown fields rejected; incomplete and invalid paths tested; no network requests; no secret written in evidence; manual diagnosis and reviewed handover retained. Tenant acceptance additionally requires baseline message, authorised own actions, functional retest and cleanup evidence. Local tests alone cannot satisfy tenant acceptance or prove the learner’s support independence.
## K. Artefacts and cleanup
Keep schema, templates, source, tests, compact outputs and a sanitised walkthrough. Private evidence retains actual operator, permissions and observations. Remove any synthetic tenant user/mailbox or licence only if you created it and cleanup is explicitly in scope; confirm with the tenant owner. Remove test messages and revoke only temporary test access you were authorised to create. Never delete pre-existing accounts. Delete private copied logs when no longer needed under the agreed retention plan.
## L. Interview story, M. Conditional wording and N. Extension
Explain the recurring handover problem, own template/check decisions, rejection of incomplete records and the limit that correct diagnosis still needs a person. Only after personally running and explaining it: “Built and tested an offline support-record checker using synthetic tickets, with missing-information checks and explicit security escalation.” If only assisted, state that contribution. Optional AI summary: compare a fixed synthetic holdout of complete/incomplete/ambiguous tickets against the rules; measure omissions and invented facts, refuse unknowns, use no live data and retain human approval. Do not add AI merely to make the application appear more aligned.

# Partner escalation evidence lab
## A Outcome and status
Check that a synthetic support handover contains the evidence a reviewer needs and belongs to the intended tenant. The code is a local checklist, not an ITSM integration or security boundary. Offline evaluation is recorded; Bunamin's personal execution, GDAP use and live vendor handover remain unrun. This is a distinct scenario inside Service-Desk-Handover-Lab.
## B Public need and basis
Partner support requires accurate history, configuration findings, business impact, evidence and ownership. Giacom's advert states these duties; its November 2025 guided billing announcement offers a related evidence-capture lesson, not proof of cloud-team tooling or measured improvement. This scenario generalises the problem without naming customers or reproducing proprietary systems. Microsoft's GDAP introduction, checked 27 October 2026, explains customer-approved, granular, time-bound partner access: https://learn.microsoft.com/en-us/partner-center/customers/gdap-introduction . No GDAP connection is built here.
## C Role mapping and D gap
Practise incident ownership through handover, approved access, technical evidence and vendor coordination. Strengthen new partner-context learning without claiming all products or direct tenant-change authority. A checklist pass is not proof that evidence is accurate, the analyst has access or a case is resolved. Existing professional support evidence remains separate from this new project.
## E Repeated task and baseline
An analyst could use a handover checklist at each escalation or shift change, potentially daily; this is a proposed repeat-use need, not validated customer demand. Baseline: inspect two dummy cases by hand for impact, history, configuration, checks, next action and owner. Target: complete case goes to human review; wrong-tenant or incomplete evidence stays on hold. No human time, escalation acceptance rate or service improvement measured. AI is unnecessary for required-field and tenant-label checks; an optional later narrative summary needs fact and privacy evaluation.
## F Architecture and security
fixtures/sample.json → Python3.10+ validation → hold or human_review plus reasons → analyst/specialist review. There are no credentials, network requests, updates, access grants or closures. tenant and evidence_tenant equality is only a dummy-data consistency check. Boolean access_authorised and sanitised are self-reported inputs. They cannot authenticate a user, detect secrets or prove authorisation. The tool does not print source narrative into its report, but local input still needs secure handling. Production needs real identity/authorisation, content inspection, tenant isolation, retention, concurrency and audit.
## G Prerequisites and cost
Personal computer, editor and Python3.10+; no packages, cloud licence or paid API. Planning budget one to two sessions plus separate supervised product learning, not measured time. A real partner-access extension needs a permitted partner sandbox and customer-approved scope; availability and cost are not assumed. Do not create a partner relationship, assign roles or grant access for this lab. A written sandbox design is a useful no-cost substitute while access is unavailable.
## H Granular local steps
1. Start with the scenario copied locally. Navigate to Modern Workplace Solutions/Service-Desk-Handover-Lab/scenarios/partner-escalation-review. Run python3 --version (Windows py --version), expecting 3.10+. Verify scripts/review.py, fixtures/sample.json and tests/test_review.py exist. If missing, recover the designated scenario; do not run a different root project's test and call this scenario checked.
2. Open sample.json in an editor. There are two synthetic cases, ESC-01 and ESC-02, with demo tenant labels and no real contacts. List the six required evidence fields from scripts/review.py. Expected: impact, history, configuration, checks, next_action, owner. These are demonstration requirements; a real vendor may require different fields. Stop if real tenant data is present.
3. Write the manual baseline before running: ESC-01 complete but still needs human review; ESC-02 on hold because evidence_tenant is demo-a while tenant is demo-b, authority false and required fields absent. Verify the actual missing keys and record them. Recovery: review the fixture rather than inventing a priority or vendor policy.
4. Run python3 -m unittest discover -s tests -v. Expect 11 checks and final OK. Review cross-tenant, authorisation string, missing checks, sanitisation, duplicate IDs and no automatic closure/access tests. If a test fails, save the failure and inspect source version. Do not replace hold with ready merely to get a pass.
5. Run python3 scripts/review.py fixtures/sample.json. Expect ESC-01 review_state human_review and ESC-02 hold with explicit reasons. Both case_closed and access_granted must be false. The owner is retained. Compare every reason with step3. If file-not-found, correct your working directory; if Input rejected, inspect syntax and required identity fields.
6. Capture your run using python3 scripts/review.py fixtures/sample.json > evidence/learner-report.json. Read the whole file. Confirm exactly two IDs and no original incident narratives in the output. Save command, interpreter, source revision and a brief explanation privately. Verify exit 0; shell redirection alone does not establish a successful or complete file.
7. Copy the fixture to fixtures/broken.json. On ESC-01 set evidence_tenant to demo-b, leaving tenant demo-a. Run the tool on the copy. Expect hold and Evidence belongs to another tenant. Verify owner remains demo-analyst and no access is granted. Restore demo-a; human_review should return. This is a consistency exercise, not a test of genuine multi-tenant authentication.
8. Remove checks from ESC-01 in the copy and rerun. Expect Missing checks and hold. Restore it with the original text; verify human_review returns. Then set sanitised false; expect a sanitisation hold. Changing a flag to true is not proof of redaction: inspect the actual contents manually before restoring it.
9. Set access_authorised to the string yes. Expect hold because only boolean true satisfies the dummy assertion. Restore true. Remove tenant or duplicate the id; expect Input rejected and exit 2. Repair the copy, rerun tests and compare original sample unchanged. Preserve failure and recovery evidence.
10. Produce a handover note outside the public repository: affected service and impact, evidence and time range, tested hypotheses, changes actually performed or none, access limit, next action, named owner, specialist question and next update time. For this exercise use only fictional names/labels. Expected: the next analyst can explain what is known, missing and proposed. Recovery: mark missing facts Unknown; do not invent a checked configuration or completed remediation.

## I Break fix and J acceptance
Required offline faults: wrong tenant label, missing check evidence, authorisation as text, unsanitised flag, duplicate ID and missing identity. Accept only if 11 tests pass, ESC-01 remains human_review, ESC-02 hold, all expected reasons appear, owner is retained and no access/closure occurs. One complete record does not validate a real escalation policy; independent review must judge factual quality and vendor requirements. Native acceptance requires real permitted/denied/expired access observations and is pending.

# Lab 2: Device and network readiness evidence
## A. Outcome and status
Build a read-only checker for a fake Windows device snapshot, then follow a separate supervised practice path to collect real test-device observations. It must keep unknown checks visible and never approve a deployment automatically. The local checker is not hardware, Intune, RMM or firewall experience. Native Windows and physical work are unrun.
## B. Company need and research
The Elevate advert includes device preparation, Windows support, connectivity checks and routine maintenance. Its security article discusses missing updates and poorly protected endpoints. Scenario hypothesis: a repeatable pre-handover checklist can help an analyst hand an incomplete device back for review. No internal Elevate process or defect was observed.
Sources checked 7 November 2026: https://elevate-cloud.co.uk/careers/support-analyst ; https://elevate-cloud.co.uk/insights/5-warning-signs-cybersecurity . The resources index gives the security article a different headline. Preserve that mismatch; the article text is the source for its content.
## C–E. Requirements, gaps and repeat use
Exercises Windows/network fundamentals, maintenance notes, evidence gathering and escalation. Directly targets the gap in personal physical-device configuration. Proven cloud diagnosis and branch guidance help the learning approach, but do not establish switch/firewall or laptop deployment experience. Use the checklist at each test-device handover and after a reported connectivity fault. This is a recurring-use hypothesis; no user adoption has been measured.
Baseline: manually read the snapshot and mark missing/failed/unknown checks. Target: match that checklist, reject malformed observations and prevent a clean software output from becoming deployment approval. Budget: 90 minutes for the local slice, then 3–4 hours for authorised physical practice with a reviewer. No success/time metric is claimed before measurement.
## F. Architecture and AI decision
Fake snapshot JSON → schema/type and IPv4 checks → findings → human handover. No network probes or changes are made by the Python code. Physical_check and patch_review are observations supplied by the operator, not independently verified by software. The IPv4 checker is deliberately limited: it does not validate subnet/gateway reachability, IPv6, routing or device health. Fixed rules are sufficient; AI would add uncertainty without a demonstrated benefit.

## H. Step-by-step local slice
1. Open a terminal in this scenario folder and run `python3 --version` (Windows: `py --version`). Expect 3.10+. If the command fails, install from the official Python source and reopen the terminal. Do not install packages; the code uses the standard library.
2. Read `sample.json`. It deliberately contains a link-local address, no recorded gateway, two failed checks and two null checks. Null means not observed, not false and not pass. Write the expected six findings in your manual baseline before running the program.
3. Run `python3 review.py sample.json`. Expect status needs review and approved_for_deployment false. Compare each finding with your baseline. If parsing fails, check that you are in the correct folder and the JSON has not been edited into invalid syntax.
4. Run `python3 -m unittest -v`. Expect ten tests. They cover missing/extra fields, unknowns, invalid addresses, string booleans, unchanged input and no automatic approval. Save actual output and runtime in evidence. A pass is local fixture evidence only.
5. Make a copy named `repaired.json` in your editor. Use the documentation-only addresses 192.0.2.10 and 192.0.2.1, set every check to true, then run `python3 review.py repaired.json`. Expect recorded checks passed but approval false. These fake addresses are examples, not settings to apply to a live network. Explain why supplied observations cannot establish deployment safety.
6. Set dns_ok to null in the copy. Run it again: expect not observed and needs review. Change it to the text "false": expect exit code 2 and a type error. Restore a valid value and rerun. Save the failed output before fixing it.
### Authorised Windows and physical extension — unrun
7. Starting state: a spare authorised PC, isolated network and reviewer. Record permission and serial/asset details privately. Inspect case, cables, ports and power supply for damage before connecting. Stop and seek a qualified technician for damaged power equipment; never open mains-power components. Connect the correct power, screen and input devices and start the PC. A VM cannot satisfy this physical step.
8. Sign in with an authorised test account. Open Settings → System → About and note Windows edition/version. Open Settings → Windows Update and record pending updates and any restart requirement. Read the state before proposing installation. Agree a maintenance window and backup/recovery approach with the reviewer; this guide does not authorise changes to managed equipment.
9. Open PowerShell on the test PC. Run `Get-NetIPConfiguration` and `ipconfig /all`. Record the active adapter, IPv4 address, subnet prefix/mask, default gateway, DNS servers and DHCP status. DHCP supplies address settings automatically; DNS turns service names into addresses. These observations are private until sanitised. If commands fail, record the error and ask the reviewer; do not disable security controls.
10. On an internet-enabled test network that permits these checks, run `Resolve-DnsName -Name login.microsoftonline.com`, then `Test-NetConnection -ComputerName login.microsoftonline.com -Port 443`. Expect name records and TcpTestSucceeded true when that destination/path is available. A true TCP result does not prove sign-in, authentication or the whole service is healthy. Failure can be DNS, proxy, routing, filtering or the remote endpoint; do not label it a firewall fault without evidence.
11. Compare your real observations with the fake schema, using a private copy. Set a flag only for a check actually performed; retain null where unobserved. A link-local address suggests checking the local link and DHCP process, not proof that a DHCP server is broken. Compare with one working test device if authorised; do not change shared DHCP, DNS or firewall settings.
12. Practise a safe fault using the offline JSON first. For a real device, disconnect only your test device's Ethernet cable after reviewer agreement; observe the adapter state, reconnect and confirm recovery. Do not disconnect a shared switch, reset a router or disable a firewall. If a connection does not recover, return to the original known state and escalate with the evidence.
13. With an owned spare PC and reviewer, install one approved business application from its official source, record version and launch it. Check the supported default printer or test peripheral if available. Do not wipe/reimage a device, enrol it in a business tenant or access personal files. If a physical peripheral is unavailable, mark that step not run.
14. Write a handover: requested use, device checks, network observations, pending updates, application test, failed/unknown items, proposed next action and owner. The reviewer decides readiness. Avoid passwords or recovery keys in notes. Have the reviewer explain which tasks you can now repeat and which need supervision.
## I–J. Break/fix and acceptance
Local acceptance: ten tests pass; malformed input exits without a report; null stays unknown; no result approves deployment; original sample remains unchanged. Physical acceptance is separate: saved authorised observations, one safe fault and recovery, application/peripheral checks and reviewer sign-off. Neither local pass nor VM work proves switch/firewall configuration or independent commercial endpoint deployment.
## K. Artefacts and cleanup
Keep a private observation sheet, sanitised screenshots, test log, manual-versus-tool comparison and before/after fault note. Record who performed each step. Remove temporary JSON copies and test accounts through the authorised owner after review. Return the spare PC and cables to their starting state. Retain only redacted public evidence, and do not export hostnames, IP inventories, serials, licence keys or tenant identifiers.

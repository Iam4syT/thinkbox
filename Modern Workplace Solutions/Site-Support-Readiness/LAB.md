# Site support readiness and safe handover
## A. Outcome and honest state
Identify incomplete device and access checks without changing a device. This is an offline Python checklist with synthetic records, not an employer system, Windows repair, MDM integration or ISO certification. The local checker was implemented and evaluated automatically on 29 October 2026; independent learner execution remains unverified. Live Windows/device/tenant exercises below remain unrun.
## B. Employer need and research basis
Public multi-site support job descriptions asks for hardware/mobile/data-access support, vendor coordination and site security contributions. Public product developments show continued change, but no internal incident or proprietary architecture is known. Hypothesis: a reviewed checklist helps repeatable handovers. Not commissioned client work.
## C. Requirement mapping
R3/R4/T1/T3/T5. Uses Office-compatible JSON/CSV concepts and Windows follow-up; Python is a chosen portable lab tool, not an advertised employer requirement. No invented ServiceNow/Intune estate or product access.
## D. Gap map
Builds structured device triage, missing-evidence handling and escalation practice. Existing M365 case work is professional reported evidence. Physical repairs, advanced infrastructure, production deployment and ISO assessment ownership remain unestablished after this local mock.
## E. Repeat-use test and baseline
A support colleague can use this at each site visit or device handover. Frequency is a design assumption, not measured employer demand. Baseline: manually inspect three sample records. Before running code, write expected results DEMO-01 ready for human review, DEMO-02 hold, DEMO-03 review. Target: exact agreement, zero automatic approval, missing evidence never silently passed. No human-time or business saving measured.
## F. Architecture, data and security
Operator → local sample.json → strict field/type validation → decision report → human reviewer. No network calls, credentials, tenant writes, privileged access or automatic remediation. Four required checks: device_checked, access_checked, security_checked, handover_checked. Exact Boolean true is a recorded assertion, not independently verified evidence. READY_FOR_HUMAN_REVIEW still requires the reviewer to inspect source evidence. A local user can edit records; tamper resistance, role enforcement and audit signing are not implemented. Only synthetic data may be published.
## G. Prerequisites, cost and starting state
Allow60–90 minutes for local exercise and2–4 hours for optional Windows practice; estimates, not measured durations. Use Python 3.11+ and a terminal, no third-party packages. Local run has no cloud/API/licence charge. Download the chosen repository project into a user-owned folder. No tenant account required. Optional device stage needs a personally owned spare Windows 11device/VM, lawful licence, backup and owner consent. Do not buy licences or change work devices for this guide. A VM gives OS practice, not physical repair experience.
## H. Granular implementation and verification
### Step1 — Open the project
Start with the downloaded project folder visible. Open Terminal (Mac) or PowerShell (Windows), type cd followed by the quoted folder path, then run python3 --version (Mac) or py -3 --version (Windows). Expected: Python 3.11or newer. Verify main.py, sample.json and test_behaviour.py are in the folder using ls or Get-ChildItem. If Python or files are missing, stop and install Python from python.org or locate the correct folder; do not run from a system directory. Below commands use python3; on Windows replace it with py -3.
### Step2 — Understand the input
Open sample.json in a text editor. It contains three fake IDs and named checks; true means supporting evidence was reviewed, false means a failed check, omitted/null means unknown. Read main.py CHECKS list and compare spelling. Expected: four exact field names. Verify the manual baseline above before running. If a field is misspelt, correct the spelling; unknown fields are rejected rather than ignored.
### Step3 — Produce the first report
From project root run python3 -B main.py sample.json --out report.json. Expected: report.json created with three records, status and failed/unknown lists. Open it and compare each ID with the manual baseline. On INVALID INPUT read the named field, repair JSON/type spelling and retry. If there is no output, check the command exit status and file permissions. Never treat a previous report as a successful new run.
### Step4 — Run acceptance tests
Run python3 -B -m unittest -v test_behaviour. Expected:9 named tests pass, including per-field false/missing/null subcases, duplicate IDs, invalid strings and failure precedence. Verify terminal ends OK; keep a local copy of output and Python version. If a test fails, retain the failure text, inspect input/logic and rerun only after a justified fix. Do not delete a failing test to obtain green output.
### Step5 — Break a check safely
Copy sample.json to fault.json. Change DEMO-01's device_checked from true to false. Run python3 -B main.py fault.json --out fault-report.json. Expected: DEMO-01 HOLD with that field named. Compare other records, which must retain their own status. Restore true and rerun to a different filename; expected ready for human review. Keep both reports to demonstrate the difference. A report is evidence about the checker, not evidence that a real device is healthy.
### Step6 — Exercise unknown and malformed data
Delete access_checked from DEMO-01, leaving valid commas. Rerun; expected REVIEW and a named unknown. Then change a Boolean to the quoted string "true". Rerun; expected INVALID INPUT and process exit2; output report must not be accepted as fresh. Restore from sample.json to recover. Delete any stale fault report or mark it obsolete before retrying. Duplicate an ID; expected rejection. Fix the ID and verify normal operation.
### Step7 — Add the human handover
Create handover.md. Write fake record ID, symptom/change request, checks personally performed, evidence filenames, what is unknown, named owner, review date and next action. For a held record, state the escalation or rollback decision and why. For a ready record, write that no live action is authorised by this report. Reviewer compares evidence to each true assertion and signs off separately. Expected: another person can explain the next safe action without guessing. If evidence is absent, change true to null and rerun; never fabricate proof.
### Step8 — Optional Windows extension, UNRUN
On your own test Windows device, open Settings → System → About and record only a fake asset ID plus OS version; never publish serial numbers or account details. In PowerShell run ipconfig /all and inspect address/gateway/DNS locally using Microsoft documentation. Check a known-good peripheral without opening mains equipment. Record observations, not automatic pass. For a fictional access issue, write identity verification and specialist escalation steps without resetting a real account. Review a synthetic security checklist for locked screen, approved patch state and authorised asset custody; this is not an ISO audit. Fill each Boolean only after observing its stated check; otherwise leave null. Verify report and handover. Restore any personally changed settings and remove private diagnostic files. If permissions or safe equipment are missing, keep this extension unrun.
## I. Break/fix and escalation
Missing evidence→REVIEW; false check→HOLD; string/duplicate/unknown-field→INVALID INPUT. Start by reading the named error and comparing the last valid sample. Recover from the supplied immutable sample, rerun and compare IDs. Do not auto-fix an organisational device, bypass permissions or equate a checklist with repair. Escalate physical damage, security indicators and uncertain access rights to the authorised specialist.

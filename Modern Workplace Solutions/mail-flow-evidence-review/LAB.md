# Lab 1 Mail flow evidence and change review
## Purpose and job link
Build a repeatable report that joins synthetic message outcomes with mailbox settings, flags missing evidence and proposes a human-reviewed next action. DWP advert requires messaging support, automation and reliable services. A recurring delivery-review need is a reasonable scenario, not a claimed DWP incident. Strengthens diagnostics, reporting, review boundaries and exact script evidence.
## Baseline architecture and costs
Baseline: manually inspect each trace and mailbox setting. Proposed improvement: deterministic checks producing the same review questions. No AI is needed to classify known statuses; an AI narrative extension would require separate accuracy/privacy evaluation. Stack: Python 3 standard library, JSON fixtures, report output; native extension Exchange Online PowerShell and EAC. Flow: dummy inputs → validation → review flags → human diagnosis → separately approved change → delivery recheck. Nothing connects to a tenant. Offline licence/cost: no additional purchase. Native extension needs two licensed test mailboxes, appropriate Exchange roles and approved tenant access; prices and licence availability must be checked before spending. Planned learning budget: one focused weekend, not a measured completion time.
## Granular offline steps
1. Open this solution’s public folder. Confirm inputs contain only synthetic example.invalid addresses. Expected: no real recipients or credentials. Stop if real data appears.
2. Read fixtures/sample.json. It contains delivered, failed and pending messages and a deliberately mismatched primary/proxy address. Record which cases manual review would flag; this is the comparison baseline.
3. Run python3 scripts/review.py fixtures/sample.json > evidence/report.json. Expected: failed and pending messages require review; SMTP mismatch requires review; delivered matching record needs no immediate action. No setting is changed.
4. Open report.json and compare every flag with the fixture. Record the row ID and reason. A pending trace is not a proven failure; do not recommend changing a connector from status alone.
5. Run python3 -m unittest discover -s tests -v. Expected: normal and failure-path assertions pass, including duplicate IDs, missing required data and unsupported statuses. Save actual output with the run date and interpreter version.
6. Copy the sample to fixtures/broken.json. Change one status to an unknown value. Run the script against it. Expected: it fails clearly; no report may be treated as complete. Restore the status and rerun. Save the failed and repaired output.
7. Copy a row with the same ID. Expected: duplicate rejection. Remove the duplicate and rerun. Verify the original sample remains unchanged.
8. Write a change-review note: observed fault, evidence, possible cause, checks needed, owner, approval, rollback and proposed delivery test. Keep suggested action separate from completed action.
## Native Exchange extension unrun
9. In an authorised isolated test tenant, record tenant name privately, Exchange role and licence for both test mailboxes. Export existing connector and mailbox settings before any approved change. Do not change customer or DWP systems.
10. Send one uniquely named dummy test message between the two permitted test mailboxes. Note sender, recipient and time; check receipt. Use EAC → Mail flow → Message trace → Start a trace; select those addresses and time range. Microsoft notes status can lag; a missing immediate row is not proof of failure.
11. Export the relevant trace results. Inspect mailbox email addresses and record the primary address privately. Sanitise into the fixture schema; keep message bodies out. Native fields may differ, so document mapping rather than pretending the fixture directly ingests any export.
12. Run the local report on the sanitised input and compare it with EAC and received message. Any discrepancy needs investigation before using it for decisions.
13. If introducing a fault, use only an approved disposable test-mailbox configuration with a recorded before-state and exact rollback. Do not enable relay, disable protections or invent a connector repair. Obtain separate live-change approval before performing this step.
14. After an approved correction, repeat the same delivery test and trace. Record result and limits; send success is not proof every route works.
## Acceptance failure recovery and cleanup
Accept only if valid delivered/failed/pending/mismatch cases are classified correctly, invalid/duplicate data is rejected, and the report never changes settings. Native acceptance additionally needs a before/after trace plus receipt check, authorised scope and a reviewed rollback. Permission errors, delayed traces, unrecognised export headers and ambiguous causes must stay visible. Restore disposable test settings from the before-state only within authorised scope; retain logs until reviewed. Remove only local generated dummy files after copying evidence you need. No purge of real mail.

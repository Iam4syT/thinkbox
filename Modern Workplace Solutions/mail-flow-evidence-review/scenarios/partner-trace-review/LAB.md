# Partner mail evidence review lab
## A Outcome and honest status
Turn a small set of synthetic Microsoft 365 message-trace observations into clear next-check prompts. The offline tool is implemented and evaluated as documented in EVALUATION.md. Bunamin's independent execution, an actual tenant connection and a real mail fault remain unrun. This is a learning scenario within the existing mail-flow-evidence-review project.
## B Public need and boundary
Cloud partners repeatedly ask why a message did not arrive. Giacom's public cloud-support advert names Exchange Online, diagnosis, approved access and technical evidence. The example workflow is an independent hypothesis about a useful repeated task, not an assertion about its internal systems, customers or ticket failure rate. The public technical basis is Microsoft's Message trace in the Exchange admin center documentation, checked 27 October 2026: https://learn.microsoft.com/en-us/exchange/monitoring/trace-an-email-message/message-trace-modern-eac . Its four statuses in this exercise are a simplified schema, not a complete Exchange export format.
## C Responsibilities exercised
Practise structured diagnosis, configuration context, checks within authority, evidence gathering and a clear next action. This does not implement a mail-flow change or prove vendor-specific backup/security expertise.
## D Learning gap
Strengthen evidence interpretation and repeatable checks. Existing professional mail troubleshooting is separate from new offline code. Learn to distinguish observed delivery status from an explanation or verified customer recovery; Delivered does not prove a message is visible in the expected inbox.
## E Recurring use and baseline
Intended user: a support analyst reviewing each mail case. Frequency: potentially daily, a design hypothesis. Manual baseline: read four dummy records and write the next check for each. Success target: agreement with the four expected prompts, refusal of malformed evidence and no automatic tenant changes. No elapsed-time saving or company benefit measured. Rules are a simpler, more inspectable baseline than AI here; no AI service is called. A later summary assistant would require factual-omission and privacy tests.
## F Architecture and security
Flow: local fixtures/sample.json → scripts/review.py validation → JSON prompts on standard output → analyst review → separately authorised diagnostics. Python3.10+ standard library; no network library, token, Graph connection, delegated privilege or mail content. Tenant labels demo-a/demo-b are synthetic and copied into output for context. access_authorised is a dummy assertion, not real identity enforcement. Never replace it with automatic trust in an imported ticket. A production adapter needs authenticated authorisation, tenant isolation, audit and secure retention.
## G Prerequisites costs and starting state
Use a personal computer, a text editor and Python3.10+. No packages, subscription or paid API needed for the offline path. Planning budget one to two learning sessions, not measured duration. Native extension needs an authorised isolated M365 tenant, two licensed test mailboxes and an approved role with sufficient Exchange access. Trial eligibility and price must be checked; do not buy a licence for this guide automatically. Without access, complete the offline work and keep native steps unrun.
## H Granular offline implementation
1. Start with the scenario folder copied locally or cloned from Thinkbox. In a terminal run python3 --version (Windows py --version). Expect 3.10 or newer. List the folder: scripts, fixtures, tests, docs and evidence should exist. If Python is absent, obtain an approved official installation; do not change a work device without authority.
2. Navigate inside Modern Workplace Solutions/mail-flow-evidence-review/scenarios/partner-trace-review. Open fixtures/sample.json. Expect four IDs MAIL-01 to MAIL-04, two dummy tenants and no real people, addresses or secrets. If real data is present, stop and replace it with dummy data before running or publishing.
3. Without changing the file, write a manual note: MAIL-01 check recipient experience; MAIL-02 inspect failure detail; MAIL-03 investigate delay and recheck; MAIL-04 stop diagnostics until authority/evidence is established. Verify each status and access_authorised value. If uncertain, read actions in scripts/review.py and explain each in your own words; record that the baseline then used supplied policy.
4. Run python3 -m unittest discover -s tests -v. Expect 10 checks and final OK for the supplied version. Read each method, including Delivered ambiguity, missing identity, duplicate ID, unsupported status and authority as a string. Recovery: retain failure output and compare source/fixture revision before editing; do not remove an assertion to get a pass.
5. Run python3 scripts/review.py fixtures/sample.json. Expect four records, each human_review_required true and setting_changed false. MAIL-04 starts Stop tenant diagnostics. Compare every next_action with step3; output must not say a tenant was repaired. If file-not-found, check current folder and spelling; if Input rejected, repair a copy of the fixture.
6. Capture a fresh run using python3 scripts/review.py fixtures/sample.json > evidence/learner-report.json. Inspect the whole JSON and record Python version, command and source revision in a private learning note. Verify all four IDs and that the source file is unchanged. A redirected file can be empty after an error; only accept it when the command exits0 and contains all four records.
7. Copy fixtures/sample.json to fixtures/broken.json in your editor. Change MAIL-02 trace_status from Failed to Closed, a deliberately unsupported status. Run python3 scripts/review.py fixtures/broken.json. Expect Input rejected and exit 2, no successful JSON report. Record the error. Restore Failed and rerun; four records should return. Recovery is correction of the schema, not calling Closed a delivery result.
8. In the copy, change MAIL-01 access_authorised to false and rerun. Expect Stop even though status is Delivered. Try the string yes; expect the same stop. Restore true and rerun. Verify no automatic access grant and no change in another record. This models conservative interpretation, not a working access-control system.
9. Duplicate MAIL-01 by copying the whole record in the test copy. Expect duplicate rejection. Remove the duplicate and rerun tests and the valid sample. Keep the original fixture unchanged. Explain why mixing evidence between cases is risky even if the syntax is valid.
## H Native Exchange extension unrun
10. Before native work, record explicit test-tenant authority, tenant identifier privately, the actual Exchange role, licensed test-mailbox pair and permitted actions. Review Microsoft's least-privilege guidance; do not grant a Global Administrator role to complete this exercise. This run changes no tenant or role. If permission is missing, stop at the offline evidence.
11. In the approved test environment, send a harmless uniquely labelled message between the two test mailboxes. Note time, sender and recipient privately, and check the receiving mailbox. Open admin.exchange.microsoft.com, then Mail flow → Message trace → Start a trace. Use the actual test sender/recipient and a tight time range. Expect a trace once processing is visible; absence immediately is unknown, not proven delivery failure.
12. Compare trace detail and the actual mailbox result. Record the observed status and next diagnostic; sanitise into the fixture schema manually, because the prototype does not ingest arbitrary Exchange exports. Keep bodies, recipient addresses and tenant identifiers out of public evidence. If export/status fields differ, document the mapping rather than silently coercing it. Do not fabricate a failure just to fill a row.
13. No fault-inducing tenant change is required. Practise failure reasoning offline. If a future test change is proposed, first document its exact before-state, authority, expected effect and rollback for review. Only a separately authorised change may be executed. Retest using the same message route and recipient check; a trace alone cannot prove every route works.
## I Break fix and recovery
The required failure exercises are unsupported status, duplicate ID and absent or string-valued authority. Preserve failed and repaired outputs. Permission-denied or delayed native traces remain unresolved observations. Never disable protections, change a connector or reconfigure customer DNS from a status label alone.
## J Acceptance and cleanup
Accept offline completion only if 10 checks pass, four expected outputs match the manual baseline, invalid input is rejected and no source/tenant state changes. Human-review flags must stay true. Native acceptance additionally requires the real role/scope receipt and actual trace plus recipient observation; it is unrun today. Remove only your newly created broken.json and learner-report when no longer needed, after saving evidence. Keep source, sample and evaluation. No mailbox purge or cloud teardown is involved.
## K Artefacts and operational handover
Keep source, fixture, test output, four-row report, docs/architecture.md, README, EVALUATION and a two-minute walkthrough. Annotate a sanitised screenshot if useful. Handover explains supported statuses, invalid input, the authority assertion limitation and how to leave a case open. A production service would also need secure storage, retention, access checks, change approvals and monitoring.

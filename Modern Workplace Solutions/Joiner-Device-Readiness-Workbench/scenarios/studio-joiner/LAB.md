# Lab 1 — Studio joiner readiness and handover
## A–E. Outcome, business context and mapping
Outcome: prepare and verify a synthetic joiner's account, collaboration access and test-device/application checklist, with an explicit reviewer and handover. The offline component checks whether the evidence record is complete; it does not create accounts or determine actual device readiness.
Scenario basis: a hypothetical multidisciplinary studio needs repeatable IT support. No employer deployment or demand has been established.
Scope: independent learning for support operations; physical and tenant work require equipment, authority and actual evidence.
## F. Architecture and boundaries
Synthetic request → human approval → test Entra/M365 user and authorised Windows test device → explicit sign-in/mail/SharePoint/app checks → reviewed handover. Offline Python checker reads only a supplied JSON record and prints ready-for-review or blocked. A boolean “true” means the operator reported a check; it is not a sensor or proof of a live configuration.
Stack: M365/Entra/SharePoint and Windows 11 lab branch; optional Intune Win32 deployment . The target workplace platform is unknown. Use of these products is a learner learning choice. No architecture-app or Adobe licence is assumed. No AI is needed for the baseline.
## G. Prerequisites, cost and plan
Offline branch: Python 3, supplied checker/templates/tests and any OS; no account or licence cost, no network calls. Allow one focused session; no measured duration claimed. Tenant/device branch: isolated owner-authorised test tenant, appropriate M365/Intune licences, permitted Windows 11 test device/VM, test users and supervisor for unfamiliar physical work. Do not buy anything or assume a free trial is eligible. Check actual licence entitlement and device capacity first; cost remains £0 for offline, variable/unapproved for cloud/device branch. Allow one to three weekends as a planning estimate.
No employer data, tenant exports, secrets, real employee names or live changes. Record operator, permission, starting state and rollback before each tenant task. Windows physical work needs actual equipment and review; a VM cannot prove cabling/peripheral competence.


## H1. Start with an auditable offline baseline
1. Starting state: supplied solution folder. Open a terminal there and run `python3 --version`. Expected: Python 3 version. Verify version starts with 3. If absent, stop and ask for an approved runtime; do not install arbitrary downloads.
2. Run `python3 -m unittest discover -s tests -v`. Expected: local normal/missing/invalid checks finish. Save actual output under evidence. Verify failures are resolved before relying on the checker. Recovery: retain the error, confirm folder and Python version, then inspect the named failing case.
3. Open `templates/ready.json` in a text editor. It contains synthetic request_id plus booleans for approval, account sign-in, mail, SharePoint, device check, app check and handover review. Expected: no names or secrets. Verify each is a real JSON boolean. If uncertain, copy the supplied template again rather than overwrite evidence.
4. Run `python3 scripts/check.py templates/ready.json`. Expected: READY FOR HUMAN REVIEW on this fixture. Verify this is fixture data, not an assertion about a real device. Recovery: if invalid, compare fields with the unchanged template.
5. Copy the template to `evidence/my-run.json`; set every check false initially. Run the same command on that file. Expected: BLOCKED with missing checks. Verify an unperformed test cannot silently pass. Never change false to true just to obtain a green result.
6. Create `evidence/approval.md` with synthetic request purpose, authorised applications/groups, reviewer, rollback and excluded actions. Expected: reviewable scope. Verify access owner approval is stated as pending unless actually received. Recovery: keep only offline work when authority is unavailable.
## H2. Prepare a test tenant — unrun
7. Starting state: authorised test tenant and licensed administrator, or stop. At entra.microsoft.com verify tenant ID/name and open Users → All users → New user → Create new user. Use a unique dummy alias such as lab-studio-joiner under your test domain and save securely. Expected: one standard test user. Verify it is neither production nor privileged. If role/licence is missing, ask the owner; do not grant yourself rights.
8. In the M365 admin centre select the dummy user → Licences and apps; assign only an approved available test licence. Expected: recorded entitlement, not necessarily immediate service provisioning. Verify the intended services and eventual mailbox availability. If no licence is available, stop that branch; do not purchase or reuse an employee's licence.
9. Open a private browser session as the dummy user. Complete the approved first-sign-in/MFA flow. Expected: sign-in succeeds under existing policy. Verify by reaching the intended tenant's M365 page. If blocked, collect the displayed error and authorised sign-in diagnostic; do not weaken MFA or Conditional Access. Mark account_signin true only on an observed success.


## H3. Access and equipment checks — unrun
10. Starting state: dummy account can sign in and mailbox is provisioned. Send a LAB-prefixed test email to a second authorised test mailbox and reply. Expected: both messages arrive. Verify recipient and Inbox/Junk location; record exact observation. Recovery: inspect service/licence/trace within authority and keep mail false until delivery is observed.
11. Starting state: test SharePoint site owned by the tenant owner. Create/identify a private test site through the authorised SharePoint process; add the dummy account to its agreed members group and a harmless document to a library. Expected: dummy user can open only that approved document. Verify allowed access in the dummy session. If provisioning/access fails, inspect membership and wait for documented propagation; do not make the site public.
12. Use a separate unapproved synthetic user to try the same document link. Expected: access denied/request-access, without exposing the document. Verify denial rather than just a missing menu. Recovery: remove accidental broad grants, retest both users and retain failure evidence. Set sharepoint_access true only after allowed and denied checks pass.
13. Starting state: authorised spare Windows 11 device/VM, no existing user files at risk. Record model/OS/build privately, device ownership, approved build method and recovery point. For physical equipment, ask the supervisor to show safe power/cable/peripheral connections before repeating them. Expected: known test starting state. Verify recovery is usable; if unavailable, stop changes. Do not dismantle hardware or alter firmware from this guide.
14. Follow the owner's approved Windows setup/join procedure for the test device. If permitted for this lab, Settings → Accounts → Access work or school → Connect → Join this device to Microsoft Entra ID, using the authorised test join account. Expected: correct test-tenant join, if edition/licence/policy supports it. Verify tenant and device record with reviewer. Recovery: use the agreed disconnect/recovery process; do not change production join, policy or network settings. A failed join remains failed evidence.
15. Sign in with the standard dummy user; check network access, keyboard/display and the approved peripheral with a harmless test output. Expected: usable test session and actual output (for a printer, a test page; scanning needs a dummy page). Verify the user's task, not just device detection. Recovery: compare approved driver/cable/queue checks with supervisor and escalate an unknown physical fault. Mark device_check only after performed checks and boundaries are written down.


## H4. Install, validate and hand over — unrun
16. Starting state: owner approves one non-sensitive test app, official installer, version, licence and uninstall method. Use the approved manual installation route first; record version and launch a harmless test file as standard user. Expected: successful use, not only installer exit. Verify correct source/version and standard-user behaviour. If installation fails, retain logs and use the vendor/owner rollback; do not disable antivirus or run an unknown installer.
17. Optional Intune branch only after the baseline: obtain approved app install/uninstall commands and detection criteria from its vendor, prepare its Win32 package with Microsoft's current tool, then Intune admin centre → Apps → Windows → Add → Windows app (Win32). Supply app information, program commands, requirements and detection rule . Expected: a reviewable package. Verify commands and test-device-only assignment with a reviewer before creation. If licensing/enrolment is absent, keep this branch unrun.
18. Assign the approved app only to a dedicated test group with the test device; sync using the authorised device process. Expected: install status and actual standard-user launch. Verify Intune detection, local version and user task agree. Recovery: remove only the test assignment and use the documented uninstall/restore route. Do not deploy broadly. Set app_check true only after baseline verification; record optional Intune result separately so manual success does not imply managed deployment.
19. Write a handover: request, approved scope, checks actually performed, result/failures, user guidance, outstanding items, owner and review. Ask reviewer to sign off and ask the dummy user/reviewer to repeat access/app tasks. Expected: reproducible handover. Verify no secrets appear. If not reviewed, leave handover_review false; record self-review honestly without inventing a mentor.
20. Update `my-run.json` only from actual observations and rerun checker. Expected: blocked until every required check is supported. Verify the output against the evidence log. Recovery: return unsupported true values to false and preserve both records. Human reviewer decides readiness; the checker cannot approve access or infer real configuration.


## I–J. Break/fix and acceptance
Offline faults: set approval false → BLOCKED; omit mail → INVALID; use string “true” → INVALID; add an unexpected field → INVALID. Restore valid synthetic schema and rerun. These check data handling, not live Microsoft integration.
Tenant faults, only with explicit permission: remove the dummy user's test-site membership → allowed test fails; restore approved membership → allowed/denied tests both pass. Omit test app assignment → app is not deployed; restore test assignment → observed install/launch. Never inject faults into shared services or a real colleague's device. Record what changed and the exact recovery.
Acceptance: every required test has an evidence link and operator; standard user signs in, sends/receives mail, accesses only approved SharePoint material, uses approved app/peripheral, and reviewer accepts handover. No tenant steps pass merely from an offline fixture. Baseline manual checklist and checker outputs agree; unknown inputs are rejected. No secrets or private identifiers in public artefacts. Time-saving claims need a timed before/after method and real sample, currently absent.
## K. Artefacts and cleanup
Keep private approval, screenshots with dummy identities, test observations, sanitized device/app records, source/tests and a short demo. Record any assistant help separately from the learner's actions. Stop if real data appears; remove it from public export and follow owner retention rules.
Cleanup in the isolated tenant only: remove lab-only app assignment and agreed test install; remove lab-created SharePoint membership/content/site only where deletion is authorised; release lab licence and delete lab-created users through the owner's documented process. Disconnect/restore the test device using the agreed recovery route. Never delete pre-existing sites/accounts/devices. Record what remained and who owns it.

# Lab 1 — Controlled device readiness and handover
## A. Outcome and status
Build a repeatable readiness record for an isolated Windows 11 test device: account, OS, network, approved software, peripheral check and handover exceptions. Local fixture checking is a separate portable demonstration; Windows and physical tasks are unrun until the learner performs and records them. This is independent learning, not a an example defence engineering organisation deployment.
## B. Company context and C. Requirements
an example defence engineering organisation’s advert requests device setup, Windows/M365 support and records (see sources below). A traceable readiness process plausibly supports an engineering workplace; no an example defence engineering organisation process deficiency is asserted. Exercise device preparation, common software/network diagnosis, documentation and safe escalation.
## D. Gaps and E. Repeated-use value
Primary gaps: recorded experience boundary physical practice, specific Windows tasks, printer setup and installation. A checklist is useful at every joiner, replacement or repair handover: a recurring task, not an AI showcase. Repeat on a second permitted device only after the first is understood. A fixture result cannot prove hardware competence.
## F. Architecture and baseline
Isolated Windows 11 machine → manual checks/read-only commands → synthetic readiness JSON → local validator → reviewed handover. Windows remains the operational stack; Python only checks the learning record. Manual checklist is the baseline. No AI is needed for five deterministic fields. Optional AI explanation later must use synthetic data and cannot approve access or determine readiness.
## G. Prerequisites, cost and boundaries
Use your own spare Windows 11 device or licensed VM with at least 4 GB RAM/64 GB storage where supported, a standard test account and a separate authorised administrator. A VM can teach OS diagnosis but cannot close physical cable/printer gaps. Do not enrol personal hardware into a real employer tenant. Use synthetic accounts, a non-sensitive test document and your own home/lab network. Check OS/hypervisor licence terms; no free tenant, free Windows licence or purchase is assumed. Set a zero-cloud-spend baseline. Obtain a permitted USB peripheral/printer for the physical extension; do not buy one without a separate decision. Allocate two weekends as a planning estimate, not measured duration.
## H1. Prepare the record and baseline
1. Starting state: public project folder available, no live systems connected. Open a terminal in its root; run `python3 scripts/check_readiness.py templates/ready.json`. Expected: READY for the complete synthetic record. Verify output contains only five check names and status, not host identifiers. If Python is missing, use an existing Python 3 runtime or complete the manual checklist; do not download arbitrary executables.
2. Copy `templates/ready.json` to a private working file. Record a fresh test ID such as LAB-DEVICE-01, operator, date, owner permission and baseline observations in private notes. Expected: a traceable learning record without personal serial numbers. Verify you can explain each field. Recovery: if real data was copied accidentally, remove it from the public working tree and retain only a private permitted record.
3. Before changing the machine, confirm who owns it, backup status, administrator permission and rollback. Take a VM snapshot where available or agree recovery for the spare device. Expected: a documented restore point; verify it is visible in the VM manager or backup tool. If recovery is unavailable, restrict the session to read-only checks. Never test failure injection on your main work device.
## H2. Collect and understand Windows state
4. On the isolated Windows 11 device, press Win+R, enter `winver` and record edition, version and build privately. Open Settings → System → About and compare. Expected: both identify the same OS. Verify against the appropriate Microsoft support lifecycle (see sources below). If it is Windows 10, investigate edition and ESU/LTSC before calling it supported; do not upgrade without a change plan.
5. Open Windows PowerShell normally and run `Get-ComputerInfo | Select-Object WindowsProductName,WindowsVersion,OsBuildNumber`. Expected: OS fields (see sources below). Compare with step 4; product naming can differ across versions, so use build/edition evidence rather than a single string. On command failure, capture the error, use About/winver and research the supported command; do not elevate reflexively.
6. Open Device Manager. Expand Network adapters and the chosen USB peripheral. Record device status and any warning. Expected: an identified device with a status message. Disconnect and reconnect only your expendable USB peripheral; verify it disappears/reappears. If a warning remains, record its code and use the manufacturer’s official support instructions; do not fetch a driver from an unknown site. Physical task stays unrun in a VM without passthrough.
7. Open Settings → Accounts → Other users. On this isolated machine, use the authorised admin account to create a standard local lab user through the available Add account/local-user options. Sign out and sign in as that user. Expected: successful standard-user session, without administrative rights. Verify by attempting to open an admin-only setting and cancelling any credential prompt. If no permission to create users, observe with a mentor and mark this step unrun; do not change identity policies.
## H3. Network, software and peripheral checks
8. In PowerShell run `Get-NetIPConfiguration` and `Resolve-DnsName example.com`. Record whether the lab adapter has an address, gateway and DNS response, privately. Expected: evidence appropriate to the lab network, not guaranteed internet access. Verify a browser can reach `https://example.com`. If DNS fails but another endpoint works, isolate DNS rather than assuming a damaged adapter. Do not change router configuration.
9. Choose an already-approved, licensed application or an official vendor installer expressly permitted for this lab. Record source, version and whether elevation is requested. Install using its documented default path, open it as the standard user and create/reopen a harmless test file. Expected: the actual user workflow works. Verify reopening, not merely installer success. If blocked, record the error and stop for admin/licence review; never disable Defender or bypass signing. If no installation is permitted, mark installation unrun.
10. Open Settings → Bluetooth & devices → Printers & scanners. Use Microsoft Print to PDF for the virtual queue exercise: print a synthetic page from Notepad, open the saved file and compare it. Expected: readable output and no pending job. Then, only with a permitted physical printer, add it using the manufacturer-supported process and print the same page. Verify paper output, queue and connection. A virtual PDF proves only queue/application practice. On failure, inspect queue, connection and driver separately; avoid restarting a shared spooler or changing a network printer without authority.
11. Inspect Settings → Windows Update and Windows Security without weakening protections. Record pending restart/update state; apply updates only if within the agreed lab change and recovery plan. Expected: known status, not a claim of compliance. Verify a required restart is completed before retesting. If a software compatibility concern appears, capture it and restore the approved snapshot rather than removing security controls.
## H4. Record, verify and hand over
12. In your private JSON set each readiness check to `pass` only after observing it: os, account, network, software, peripheral. Set any unrun or failed check to `pending` or `fail`. Run the checker against this file. Expected: READY only if all five pass, otherwise REVIEW. Verify a failed printer check blocks readiness even when M365 works. Recovery: correct observations, not the checker result; retain the failed run as evidence.
13. Write a handover note: device test ID, user task tested, evidence, outstanding exceptions, current state, next owner and date. Ask a mentor to compare note and machine if available. Expected: another person could see what remains unresolved. Verify no private identity/device data enters the public copy. If no reviewer, label self-review and leave external validation pending.
## I. Break/fix exercises
On the isolated test machine, disconnect/reconnect the lab USB peripheral; verify the symptom and recovery. In the JSON, change network to fail; expect REVIEW, restore after actual recheck. Remove the account field; expect a nonzero invalid-input error, restore from template. Never disable security or inject faults into a tenant. Record what you predicted, observed and corrected, including failures.
## J. Acceptance and evaluation
Acceptance: OS evidence, standard-user check, verified network workflow, authorised application workflow, truthful virtual/physical printer status, retained failed readiness run and complete handover. Portable automated acceptance requires complete→READY, failed/pending→REVIEW, missing/bad fields→error. Keep fixture tests and personal device verification separate. No timing/productivity result is claimed. Windows/physical completion is pending even if the local checker passes.
## K. Evidence, cleanup and L. Interview story
Keep sanitised screenshots, checklist, baseline, command output, failure/recovery notes and operator identity privately. Publish only synthetic derivatives after review. Uninstall the lab application if required, remove the lab user and local test files, remove the test printer and restore the snapshot where appropriate; confirm your normal account and network still work. Do not remove a shared queue or cloud identity. Interview structure: recurring setup need → own checks → Windows/tools → observed readiness and exceptions. Explain the gap honestly if you have only executed fixtures.
## M. Conditional wording and N. Extension
Only after personal completion: “Practised Windows device-readiness checks in an isolated lab, recording account, network, software and peripheral verification and documenting recovery from test faults.” This remains project evidence. Optional extension: an approved M365 test account/sign-in and a manager-approved endpoint policy lab; licences, tenant permission and device ownership must be established first. No unattended remediation or production onboarding implied.

# Joiner device readiness lab

## A Outcome and present state
Build a repeatable check for a new colleague's account, Windows laptop and Android work profile before handover. The local CSV checker is built and assistant-tested. All Windows, phone, tenant, imaging and user handover steps below are unrun. A ready CSV row is a simulation, not proof that a device works. The learner must reproduce and explain the work before adding it to his own evidence.

## B Company problem and research basis
A purpose-led law firm asks its service desk to prepare joiner accounts and hardware, enrol phones in Intune and keep asset records. Its October 2026 specification describes a 13-person IT team with infrastructure, applications, service desk and training colleagues. Hypothesis: one shared readiness record could help these people spot missing checks before a new colleague starts. This is an independent learning scenario, not commissioned work or a claim about the firm's actual process.

## C Job requirements and D Candidate gaps
This lab covers account setup, Joiners Movers Leavers (JML), Windows setup, mobile device management (MDM), Intune enrolment, software checks, inventory and documentation. It builds from professional account support and first-line Intune troubleshooting. Physical setup and full hardware onboarding remain gaps. Windows enrolment and Android work-profile practice cannot establish Apple support, printer repair, estate ownership or a full production imaging service.

## E Repeat use and baseline
User: service-desk analyst. Frequency: every joiner or replacement device. Baseline: manually check the nine fields on a paper checklist. Proposed value: show missing checks consistently before handover. Measure mismatches between the checker and an independently completed checklist on the same rows; measure time only during an actual timed run. No saved time or employer benefit has been measured. Rules are enough for fixed yes/no checks. AI adds uncertainty and cannot approve access.

## F Design and G Prerequisites
Data flow: synthetic request → approved test account → isolated Windows device and Android work profile → checks → CSV record → local report → human sign-off. The script never creates an account or changes a device. It trusts the CSV, so a dishonest or stale row defeats it.
Use Python 3.10 or later for the free offline part. Online practice needs a separate Microsoft 365 test tenant, a supported Windows Pro or Enterprise VM/device, an Android test phone, internet and suitable Microsoft 365, Intune and Entra licences. A VM does not demonstrate physical hardware handling. Microsoft Windows automatic enrolment guidance requires Intune and Entra P1/P2. Use existing authorised test licences if available; trial eligibility and cost must be checked before signup. Do not buy or activate a paid trial as part of this guide without approval. The lower-cost fallback is the CSV exercise; mark device/tenant checks unrun. Allow 1–2 hours offline and one to three weekends for supervised device practice; these are estimates, not measured durations.
Test accounts: lab.alex and lab.jordan, using the tenant's own test domain. Synthetic matter name: Demo Matter 001. No client documents. Use a disposable lab device with no personal files; keep the tenant's original admin account separate and out of the test group. Obtain the lab owner's permission before every online change. Do not use the firm's tenant.

## H Part 1 Run the local check
1. Open a terminal in this project's root. Run `python3 --version`. Expected: Python 3.10 or newer. Check the printed version. If missing, use an already available Python runtime; do not download random installers.
2. Open `data/joiners.csv` in a text editor. It has id plus approved, account, license, mfa, device_enrolled, compliant, app_test, asset_record and handover. All nine must be yes. Expected: three synthetic records. Verify that there are no real names, passwords or device serials.
3. Run `python3 scripts/check_readiness.py data/joiners.csv`. Expected: LAB-J01 READY; LAB-J02 HOLD for device_enrolled, compliant and handover; LAB-J03 HOLD for approved. Match every result to the CSV manually. If the file is not found, check your current folder and spelling.
4. Run `python3 -m unittest discover -s tests -v`. Expected: eight passing checks. Save the output in your own dated run log. A test failure means stop and inspect the named case; do not change an expected answer only to pass.
5. Save a copy as `data/my-joiners.csv`. Change LAB-J01 mfa to blank. Run the checker on your copy. Expected: HOLD with mfa missing. Restore yes and rerun. Expected: READY. Keep both outputs as a break/fix pair.
6. Remove the license column in a second copy and rerun. Expected: non-zero exit and Missing required column; no readiness decision. Restore the original header. This tests an incomplete export, not a tenant licence failure.

## H Part 2 Prepare the test account
7. Before opening an admin portal, write a change note: test tenant name, test devices, lab owner, test group, planned changes and rollback. Expected: explicit scope approval. If permission or licences are missing, stop online steps and keep them unrun.
8. In the Microsoft 365 admin centre, go to Users → Active users → Add a user. Enter the synthetic name Alex Lab and a unique username in your test domain. Select the correct usage location, assign an available test licence and keep the user a normal user. Expected: one account in Active users. Verify the username and licence; never put a temporary password in a screenshot or CSV. If a licence is unavailable, record the issue and leave license=no.
9. Sign in as the test user in a separate browser profile. Follow the tenant's existing MFA registration process. MFA means using a second sign-in check. Expected: the account can sign in with the required check. Record only pass/fail. Do not disable the tenant's security defaults or broad policies to make the lab work. If blocked, record the error and ask the lab owner to inspect the sign-in log.
10. In Entra admin centre, create a security group named LAB Joiner Devices and add only the test user. Expected: one intended member. Reopen membership and verify it. Use the smallest approved admin role for each task; initial enrolment configuration may require the tenant admin. Do not keep the user as an administrator.

## H Part 3 Enrol Windows and check hardware
11. On the isolated Windows device, confirm edition, update status and that it has no important data. On a real laptop, check charger, battery, keyboard, touchpad, display and Wi-Fi with a supervisor. Expected: each physical check has a recorded result. VM results must say virtual; they do not satisfy physical setup.
12. In Intune admin centre, go to Devices → Device onboarding → Enrollment → Windows → Automatic Enrollment. Ask the lab admin to set MDM user scope to Some and select only LAB Joiner Devices. Record the previous setting. Expected: only lab users are in this test scope. Reopen and verify the group before saving. If your portal route differs, use the checked Microsoft documentation; do not set All as a shortcut.
13. On the test Windows device, open Settings → Accounts → Access work or school → Connect. Choose Join this device to Microsoft Entra ID when available and sign in with the test account. Read and confirm only the intended test organisation. Expected: connected work account and an Entra joined device. Check Settings and run `dsregcmd /status`; AzureAdJoined should show YES for this join path. If the device is already managed elsewhere, stop and use a clean lab device.
14. In Intune Devices → All devices, find the test device. Record a synthetic asset ID, actual OS version and last check-in privately. Expected: one matching managed device. If missing, check licence, group scope, internet, time and enrolment errors. Save the error code; do not claim enrolment from the Settings label alone.
15. In Devices → Compliance → Policies, create a Windows policy for the lab with a password requirement supported by your device. Assign only the test group. A compliance policy checks whether a device follows a rule. Expected: policy assignment and, after sync and evaluation, a reported state. Open the device's policy report; record the timestamp and exact result. Pending is not compliant. Do not add a broad Conditional Access block in this exercise.
16. Sync the device through its Access work or school information page, then recheck Intune. Expected: a new check-in and a final compliance state. Fix the stated issue on the lab device and retest. If it remains pending, save the pending state and wait for normal policy evaluation; do not set compliant=yes in the CSV until observed.
17. Open the licensed Office app or web app available to the account. Create a synthetic document, save it in the test user's approved location, close and reopen it. Expected: content remains and the intended user can access it. Test with a second unauthorised test account; it should not gain access. Record each result; do not claim legal application proficiency from this Office test.
18. Discuss imaging with a supervisor: approved image, device model, backup, drivers, encryption and recovery. Image only a disposable authorised device using its supported process. Expected: a build log and successful reboot, driver and sign-in checks. There is no universal imaging command in this guide. Without the actual approved tool and supervisor, record imaging as unrun rather than substituting enrolment for imaging.

## H Part 4 Enrol a test Android work profile
19. Ask the tenant owner to confirm Android Enterprise prerequisites, including the Managed Google Play connection and an allowed personally owned work-profile enrolment route. Expected: documented availability. If absent, leave the phone section unrun; do not substitute Apple steps or reset a personal phone.
20. On the consenting test phone, first ask the lab owner which enrolment method is enabled. For the current web route, open aka.ms/enrollmyandroid in a supported browser and follow the test-tenant prompts. Use Company Portal enrolment only where the tenant still supports that older route. Do not turn on tenant-wide web enrolment just for this exercise; Microsoft says this change cannot be reversed. Expected: a separate work profile and a matching device record in Intune. Verify the managed app icon and the portal record. Keep personal data out of screenshots. No factory reset is needed for this chosen personally owned work-profile path.
21. Open a permitted work app and record sign-in, policy and sync results. Expected: the intended test account works inside the work profile. If blocked, collect the enrolment or Intune app message, device platform and check-in state, then inspect the test policy with the lab owner. Do not claim Android support from a CSV record alone.

## I Failure practice and J Acceptance
22. Remove only the test user's lab enrolment scope membership before trying a second disposable Windows device. Expected: automatic enrolment may fail or not run; collect actual observations. Restore membership and repeat the approved enrolment path. Verify the Intune record after repair. Do not remove an already enrolled device expecting that alone to unenrol it.
23. Keep one simulated handover field as no even when other fields pass. Expected: HOLD. This proves human handover cannot be inferred from a technical check. Have a second person compare the record with actual evidence before changing it to yes.
24. Acceptance: all eight offline tests pass; expected three-row output matches; incomplete schema fails safely; no live changes are performed by code. Online acceptance additionally needs actual account/MFA/device/compliance/app/asset/handover evidence. Record exactly which checks ran. No physical or tenant acceptance is asserted by the current assistant run.

## Cleanup and evidence

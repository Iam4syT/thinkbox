# Lab 2 — Azure deployment validation and operational handover
## A. Outcome and honest state
Build an isolated Azure workload with a private VM, restricted storage and repeatable security/operability evidence. Local checker and fixtures implemented and tested by the assistant; Azure configuration, Bicep deployment and cloud acceptance unrun. This is a small learning environment, not a landing zone or client implementation.
## B. a Microsoft cloud consultancy context
a Microsoft cloud consultancy publishes Azure migration/modernisation, cost optimisation and resilience consultancy. These are current service offerings; claimed customer improvements are employer statements. Scenario inference: a customer delivery team needs to show a newly built workload is secure, recoverable and supportable. ResearchCo's synthetic file-processing workload is a plausible example, not an a Microsoft cloud consultancy architecture or commissioned project.
## C. Job mapping
Role skills: Azure identity, compute, networking, security and management; configuration, troubleshooting, test evidence and handover. Storage/workload access and a private VM exercise different delivery concerns from Lab 1's M365 wave checks.
## D. Gap mapping
Targets Azure breadth, independent evidence capture, RBAC, networking and monitoring. Builds on reported Bicep/Git practice without inventing the original resource types. Does not prove Defender incident response, enterprise design or production availability.
## E. Repeated use and baseline
Use at each deployment and operational handover. Consultant captures configuration, reviewer verifies evidence, support team uses runbook. Baseline: manual six-control checklist. Success target: invalid/missing/failed security evidence never treated as complete. No actual time/cost saving measured. Deterministic checks suit these gates; AI adds no core benefit. Optional support-note drafting must be compared with source-grounded human notes.
## F. Architecture
Test subscription -> dedicated resource group -> VNet/private subnet and VM without public IP -> restricted StorageV2 account -> Entra-controlled management operations -> Activity Log alert and explicit recovery test -> local evidence flags -> human handover. Cloud identities and secrets remain private. VM guest actions use authorised Run Command; no RDP/SSH exposed to internet. Activity log monitors management actions, not guest workload logs.
## G. Prerequisites and cost
Offline: Python 3.10+, project files; no cloud accounts, £0. Cloud: explicitly authorised test Azure subscription, paid/free credit checked, deployment role for resource group; separate privileged reviewer for role assignments, notification recipient and SSH public key. MFA protects admin access. No subscription-wide Owner grants for convenience. Suggested spend ceiling £20 and one active lab day are planning limits, not vendor quotes or incurred spend. Check current regional VM/disk/storage/alert pricing; budget alerts are not a spending cap. Stop before deployment if cost approval/access missing. Plan two weekends; actual duration unmeasured. Lower-cost lane: offline checker only, no Azure completion claim.
## H. Granular implementation
### Step 1 — Bound the environment
Start: no cloud resources. Action: write private scope with subscription identifier, UK region if available, resource group rg-research-delivery-lab, named administrator/reviewer and deletion owner. Record planned maximum spend, shutdown/deletion date and the six acceptance controls. Expected: scope/budget approval. Verify: Azure account identifies intended test subscription. Recovery: tenant/subscription mismatch -> stop; never proceed using customer credentials.
### Step 2 — Run local checks first
Action: from public/ run python3 scripts/check.py templates/sample.json and python3 -m unittest discover -s scripts -p 'test_*.py' -v. Expected: CHECKS_PASS on synthetic flags and six test methods pass. Run templates/failure.json; expected HOLD and exit 1. Remove monitoring_verified in a copied local-evidence.json; expected REVIEW. Replace true with string true; expected INVALID. Verify outputs and exit semantics. Recovery: use a supported Python runtime and correct directory; do not hide failed controls.
### Step 3 — Create group and spending visibility
Action: Azure portal > Resource groups > Create; select scoped subscription/region and rg-research-delivery-lab. Add tags purpose=training and owner=lab-owner (no real personal contacts). In Cost Management create a reviewed budget for the available scope with alert thresholds and approved private recipients. Expected: dedicated empty group, budget visibility. Verify group/subscription and alert recipients. Recovery: unsupported budget scope -> arrange subscription owner review; spend limit still needs manual monitoring. No claim of enforced cap.
### Step 4 — Create restricted storage
Action: portal > Storage accounts > Create; select group; choose globally unique lowercase name, Standard LRS StorageV2. Require secure transfer, minimum TLS 1.2 and disallow blob anonymous access. Under Networking choose access from selected networks; do not leave all networks open. Initially add only the agreed test IP for blob upload if authorised, then remove it after seeding. Create synthetic-input container with private access and upload harmless hello.txt. Expected: no anonymous blob read, private container and scoped network entry. Verify Configuration and Networking, and test unauthenticated request fails. Recovery: upload blocked -> inspect current IP, network rules and data-plane role; do not turn off security settings as a convenience.
### Step 5 — Build private network
Action: portal > Virtual networks > Create in group; name vnet-research-lab, address 10.70.0.0/16; create sn-workload 10.70.1.0/24. Create nsg-research-lab and associate with sn-workload. Keep inbound deny from internet; no 0.0.0.0/0 SSH/RDP allows. Add Microsoft.Storage service endpoint on the subnet; add this subnet to storage selected-network rules. Expected: private network path eligible for storage access. Verify exact subnet rule and NSG effective rules. Recovery: subnet CIDR conflict -> correct only lab values; service endpoint alone does not grant identity access.
### Step 6 — Create private compute
Action: portal > Virtual machines > Create; choose Ubuntu LTS, smallest supported size within reviewed budget, scoped group/region. Authenticate with supplied SSH public key; choose existing VNet/subnet, no public IP and no public inbound ports. Use a Standard disk and leave paid add-ons off unless explicitly reviewed. Enable system-assigned managed identity. Before Create inspect cost estimate and resource names; stop if over budget. Expected: running private VM and managed identity. Verify NIC has no public IP, NSG has no broad inbound permit, identity exists. Recovery: region/size unavailable -> compare a cheaper permitted region/size and recheck cost; never expose a public port for workaround.
### Step 7 — Apply least privilege
Action: storage account > Access control > Add role assignment; authorised reviewer assigns Storage Blob Data Reader to the VM's managed identity at the specific storage account. Lab uploader gets only the necessary data role at this account. Reader/test operator receives scoped Reader for inspection, not Owner. Record role/scope privately. Expected: workload read rights only. Verify assignments, inherited rights and no Blob Contributor on VM. Recovery: wrong principal -> remove lab-only mistaken assignment and pick identity from VM Overview; allow propagation and retest without widening scope.
### Step 8 — Test identity and network independently
Action: VM > Run command > RunShellScript, run uname -a and confirm guest execution. Open the delivered scripts/vm_read.py locally, review it, then paste its content into the RunShellScript editor using a heredoc to create /tmp/vm_read.py on the VM. Run python3 /tmp/vm_read.py https://YOURACCOUNT.blob.core.windows.net/synthetic-input/hello.txt after replacing only YOURACCOUNT with your scoped account name. The script requests the VM identity token from the documented metadata endpoint, reads the blob using Bearer authentication and prints only HTTP status, size and SHA-256. Source syntax checked locally; Azure execution unrun. To create the file, use cat > /tmp/vm_read.py <<'PYCODE', then paste the source, then a line containing PYCODE, followed by the python3 command. If Python is absent, stop and use the Ubuntu package manager only within the approved VM. Compare the returned hash with the local source hash. Do not echo/store token. Use tenant-specific account URL privately, not in repo. Expected: hello.txt retrieved with scoped identity over allowed subnet. Verify status/content, no anonymous access and no token in logs. Recovery: 403 -> distinguish RBAC, token audience, subnet/service endpoint and firewall; wait for role propagation, inspect only scoped resources. Token handling script must be reviewed before execution; cloud read exercise source is provided and syntax checked, but not executed against Azure.
### Step 9 — Add actionable monitoring
Action: Monitor > Alerts > Create alert rule; scope group, signal appropriate storage write operation from Activity Log, condition includes the scoped account; action group sends to authorised private lab owner. Give name lab-storage-change. Trigger a harmless tag update and inspect Activity Log/alert history. Expected: management event and notification according to supported operation/evaluation. Verify both event and received alert, recording propagation delays as observed. Recovery: no signal -> inspect recorded operation name and rule scope; no notification -> inspect action-group configuration/recipient consent. Alert creation alone does not prove delivery.
### Step 10 — Prove recovery
Action: enable blob soft delete with a short approved retention period in Data protection. Retain source hello.txt and its hash privately. Delete only the synthetic blob, then use Show deleted blobs > Undelete. Download and hash the restored blob. Expected: exact content restored. Verify hash equals source. Recovery: retention not enabled -> use retained local source and mark recovery control failed until retested; do not claim soft-delete success from a re-upload. This does not establish VM backup/disaster recovery.
### Step 11 — Break network access
Action: remove only the lab subnet's storage firewall entry; repeat authenticated read. Expected: blocked data access; set network_scope_verified false and record HOLD. Restore the specific subnet entry and retest. Expected: allowed managed-identity read while anonymous/external disallowed case still fails. Recovery: missing endpoint -> inspect subnet service endpoint; never enable all networks to obtain a pass. Keep fault and retest evidence.
### Step 12 — Break and repair permissions
Action: reviewer removes the VM's lab Blob Reader assignment, waits for propagation/token expiry as required, and repeats read. Expected: 403 even though networking is correct. Restore only scoped Reader and retest; record actual delay and result. Expected: successful read. Recovery: cached token -> acquire fresh token and record uncertainty; do not mislabel immediate success as effective revocation. Never remove broad inherited roles without owner review.
### Step 13 — Build deployment practice without exaggerating IaC
Action: export group template for inspection and compare resources/parameters with actual configuration. If using Bicep, write or convert a minimal storage/VNet template in a separate lab branch, remove generated secrets, and run az bicep build --file main.bicep, then az deployment group what-if --resource-group rg-research-delivery-lab --template-file main.bicep. Expected: syntax build and reviewed intended changes only. Verify resource coverage; exported templates may omit role assignments or secrets and are not automatically complete IaC. Recovery: unexpected replacement/delete -> halt, correct scope, rerun what-if. Do not apply before owner approval. Bicep template generation/deployment remains planned here; original Bicep practice is separately reported.
### Step 14 — Capture checks and handover
Action: populate local-evidence.json from evidence: https_only = secure transfer/TLS; anonymous_access_disabled = config and negative test; network_scope_verified = subnet allowed and external denied; least_privilege_verified = exact role and revoked/allowed tests; recovery_verified = undelete/hash; monitoring_verified = event and received alert. Run checker. Expected: CHECKS_PASS only for verified complete controls. Verify every flag against private evidence and reviewer confirmation; missing -> REVIEW. Write handover with resource list, access boundaries, costs, support owner, diagnostic branches, known limits and deletion date. No resource or CHECKS_PASS authorises real production release.
### Step 15 — Cleanup and cost review
Action: stop/deallocate VM while gathering evidence; recognise disks/storage may still charge. After owner approval delete only rg-research-delivery-lab, confirm named VM/NIC/disk/storage/network removed, and inspect remaining alerts/action groups/budgets for any scoped resources needing separate removal. Expected: no active lab resources and an actual spend report once billing catches up. Verify resource inventory and Cost Management next day. Recovery: deletion failure -> inspect dependencies/locks; involve owner without removing unrelated locks. Never promise zero bill from deallocation alone.
## I. Failure exercises
Steps 11–12 separate network and authorisation faults. Step 10 distinguishes restore from re-upload. Missing monitoring or provenance keeps REVIEW. Capture own observations, hypotheses, checks, fix and limits.
## J. Acceptance
Local six-method test suite and CLI normal/failure checks pass. Cloud acceptance requires private VM, allowed authenticated blob read, denied anonymous and disallowed network reads, scoped role revocation/recovery, matching undeleted content, alert receipt and cost/deletion evidence. Cloud criteria unrun. No guest application SLO, Defender coverage, production backup or Azure landing-zone completeness claimed.
